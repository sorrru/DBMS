# 基于 MongoDB 的版本化问卷系统第一阶段项目报告

本项目完成了一套可本地运行的版本化问卷系统，覆盖账号认证、问卷草稿、四种题型、条件跳转、发布版本、公开填写、重复限制和按版本统计。系统以 MongoDB 不可变版本快照为核心，通过事务、条件更新和唯一索引维护并发不变量，并在前后端共享答案与路径语义。最新完整回归包含 28 个测试文件、184 项测试，另以固定种子数据、`explain()` 和四组浏览器流程验证数据库设计与交互结果。

## 第 1 章 项目概述

### 本章要点

- 第一阶段交付的是完整可运行系统，不是静态原型或只含数据库脚本的演示。
- 核心目标是让问卷内容、填写路径和回答始终绑定具体发布版本。
- MongoDB 设计、后端正确性、AI 使用过程和人工验收均保留可追踪证据。

### 1.1 项目背景

普通问卷在发布后直接覆盖题目，会使旧回答失去原始语境：选项文字、必答条件或跳转路径一旦改变，后续统计便可能把不同含义的数据混在一起。本项目以“每次发布形成独立版本”为中心，把问卷编辑、发布、填写和统计连成完整流程。创建者可以保留旧版本继续解释历史回答，也可以从当前版本创建下一草稿；填写者打开问卷时固定到当时的发布版本，提交和统计都不会被后来修改影响。

课程要求同时强调 MongoDB 设计和 AI 编程过程。本项目因此不仅实现页面与接口，还把集合边界、嵌套方式、索引、事务、聚合、并发控制和隐私取舍作为主要成果。开发采用分阶段的人机协作：AI 提出候选和实现，项目负责人逐轮检查、否决或修改，再用自动测试、数据库实验和浏览器操作确认结果。

### 1.2 第一阶段目标

第一阶段目标分为五类：

1. 建立可复现的 Vue、Express、MongoDB 单节点副本集开发环境；
2. 实现用户认证、问卷创建、题目与跳转编辑、发布和版本历史；
3. 实现匿名或实名填写、会话恢复、服务端路径重算和每版本重复限制；
4. 实现严格按发布版本隔离的统计、文本回答分页和实名提交记录；
5. 提供数据库设计、API、实验、测试追踪和真实 AI 使用日志，使成果可以检查和继续演进。

### 1.3 完成情况

系统已实现五个业务集合、29 条 HTTP 路由和三个 TypeScript 工作区。创建者能够完成“新建问卷—编辑设置和题目—配置跳转—检查与预览—发布—查看历史和统计”的完整链路；填写者能够完成“查看摘要—登录—创建或恢复会话—逐题填写—复核—提交”的完整链路。匿名模式对创建者隐藏直接身份，实名模式提供逐次提交账号记录；二者都使用内部所有权键执行会话和重复提交规则。

截至 2026 年 10 月 21 日，里程碑 1 至 10 已完成自动检查和人工验收。完整测试为共享逻辑 11 项、API 147 项、Web 26 项，共 184 项；10,000 份问卷列表和 50,000 份回答统计实验提供索引与聚合证据。第一阶段结论是：当前实现在课程规定的本地单进程、MongoDB 单节点副本集环境中达到既定功能和一致性目标，同时保留了生产多实例、密钥轮换和更强匿名保护等明确边界。

## 第 2 章 需求分析

### 本章要点

- 同一账号既可以创建问卷，也可以作为填写者，不设置固定角色字段。
- 匿名是对创建者隐藏身份的问卷内假名化，不等于系统完全不知道填写者。
- 发布版本不可修改、回答按版本隔离和服务端重算路径是三个核心不变量。
- 删除整份问卷、归档、多实例部署和令牌撤销不属于第一阶段范围。

### 2.1 使用者与使用场景

系统有三种访问状态，而不是三类永久账号角色。未登录访问者可以查看公开问卷摘要，但不能开始填写；登录用户可以创建和管理自己的问卷，也可以填写其他公开问卷；问卷所有者可以编辑草稿、发布版本、关闭或开放问卷，并读取自己发布版本的统计。所有者校验来自 `surveys.ownerId`，越权读取统一按不存在处理，避免泄露资源是否存在。

创建者的主要场景包括：维护仅自己可见的管理名称；设置公开标题、说明、身份模式、重复开关和截止时间；创建单选、多选、文本和数字题；配置按顺序第一条命中的跳转规则；发布前检查循环、不可达和重复规则；预览后发布；从当前版本创建下一草稿；查看版本历史、回答统计、文本内容和实名提交记录。

填写者的主要场景包括：从稳定公开链接进入；了解匿名或实名提示；登录后创建 30 分钟会话；按实际路径回答；刷新或同账号重新登录后恢复；提交时接收字段级错误；在禁止重复的版本中只能成功提交一次。公开链接发布新版本后保持不变，新打开的会话进入最新版，旧活动会话仍使用原版本。

### 2.2 功能需求

**问卷和版本。** 新问卷先创建 v1 草稿。草稿允许修改，所有写入共享一个 `revision`；发布后内容只读，修改必须从当前版本复制出下一草稿。每份问卷最多一个草稿，放弃下一草稿不会删除当前发布版本或产生版本号空洞。手工关闭与截止到期分别显示，发布新版本不自动重新开放问卷。

**题目、跳转和校验。** 题目数组顺序就是问卷顺序。跳转规则按保存顺序检查，第一条命中生效，未命中进入下一题。草稿可以暂存回跳，但自跳转在保存时拒绝，形成循环则禁止发布。必答只约束本次真实路径上的题目；服务端不信任客户端路径，提交时必须重新计算。手机号作为文本保存，并用 ASCII 数字和长度规则校验，避免丢失前导零。

**身份与重复提交。** 创建者可以按版本选择匿名或实名，并决定是否允许重复。匿名仍要求登录，系统用问卷内 HMAC 假名识别同一账号；同一问卷跨版本的所有权键稳定，不同问卷不同。禁止重复时限制范围为“同一账号、同一版本一次”，填写过 v1 不妨碍填写 v2。实名回答关联账号并向创建者显示，匿名会话和回答不保存直接用户引用。

**填写和统计。** 填写会话固定版本且默认 30 分钟有效。问卷关闭、绑定版本截止或会话到期都会阻止新的有效提交，但已经成功提交的同一会话重试仍返回原结果。统计必须明确选择发布版本，不自动合并不同版本；每题区分到达、回答、未到达和到达未答，选择题计数选项，数字题返回计数、平均值和极值，文本题分页显示内容。

### 2.3 非功能需求

系统需要满足以下可检查要求：

- **一致性：** 跨集合发布、创建或放弃草稿、正式提交使用事务；并发修改使用 revision 条件更新；最终唯一性由数据库索引兜底。
- **安全：** 密码不明文保存，JWT 固定算法和两小时有效期，Cookie 使用 HttpOnly 和 SameSite，写请求校验 Origin，请求字段按类型与白名单验证，并限制正文和请求频率。
- **隐私：** 匿名接口不返回账号、内部假名键、回答 ID 或精确提交时间；敏感分页游标提供机密性而不只是防篡改。
- **性能：** 创建者列表、版本历史、会话、回答和统计查询有对应索引；大规模实验使用固定数据和 `explain()` 检查执行计划。
- **可复现：** Node、依赖和 MongoDB 镜像固定版本；README 提供从零启动；种子和基准脚本只允许安全的本地数据库。
- **可维护：** 共享纯函数统一前后端语义，稳定错误码和 `details.path` 支持前端定位，设计与测试证据按里程碑维护。

### 2.4 第一阶段范围边界

第一阶段不提供删除或归档整份问卷，也不提供跨版本自动合并统计。登录令牌不刷新且不能由服务端即时撤销；限流保存在单进程内存，多实例部署需要共享存储。匿名是对创建者的假名化，持有服务端密钥和用户数据的运维人员仍可能重新识别；密钥直接轮换会破坏既有所有权和去重。浏览器草稿存在 `sessionStorage`，仅用于恢复非凭据答案，不能替代服务端正式保存。

## 第 3 章 系统总体设计

### 本章要点

- 系统采用 Vue 前端、Express API、共享业务逻辑包和 MongoDB 四层结构。
- 浏览器只负责交互和即时提示，最终权限、路径、截止时间与答案由服务端判断。
- 单节点副本集提供本地多文档事务能力，部署结构保持简单且可复现。
- 模块边界围绕认证、问卷版本、填写提交和统计四类业务划分。

### 3.1 总体架构

**图 3-1 系统总体架构图**

```text
┌────────────────────────── 浏览器 ──────────────────────────┐
│ Vue 3 + Vite                                               │
│ 创建者工作台／问卷编辑与预览／公开填写页／统计页             │
│ survey_session Cookie + 按会话 Path 限定的 survey_fill Cookie │
└────────────────────────────┬───────────────────────────────┘
                             │ HTTPS / JSON API
┌────────────────────────────▼───────────────────────────────┐
│ Express API                                                │
│ 认证与来源校验／问卷版本服务／填写会话与提交／统计聚合       │
└───────────────┬──────────────────────────┬─────────────────┘
                │ 调用纯函数               │ Mongoose + 事务
┌───────────────▼──────────────┐  ┌────────▼────────────────┐
│ packages/survey-logic        │  │ MongoDB 8.0             │
│ 答案校验、路径、发布检查、状态 │  │ Docker 单节点副本集 rs0  │
└──────────────────────────────┘  └─────────────────────────┘
```

单节点副本集使本地环境能够使用 MongoDB 多文档事务，同时保持课程项目的启动和检查成本可控。前后端共同依赖无数据库副作用的 `survey-logic`，避免预览、正式提交与发布检查各自实现一套规则。

### 3.2 模块划分

**前端。** `apps/web` 负责认证表单、问卷列表、草稿编辑器、只读版本、填写流程和统计展示。它使用相对 `/api` 路径通过 Vite 代理访问后端，浏览器自动携带 Cookie。前端保留未保存卡片和安全草稿，执行即时校验与路径预览，但不会把本地结果当成服务端最终结论。

**API。** `apps/api` 按认证、问卷、公开填写和统计拆分路由与服务。中间件统一处理来源、媒体类型、正文上限、认证、限流和错误格式；服务层负责所有权、状态、事务与条件更新；Mongoose 模型声明字段和索引。统计服务把多条聚合放入同一只读快照事务，保证一个响应中的指标来自同一数据时点。

**共享逻辑。** `packages/survey-logic` 不访问网络或数据库，提供答案规范化、下一题判断、路径计算、发布检查和状态计算。API 使用它执行可信校验，Web 使用它提供相同语义的即时反馈。生产构建先编译共享包，再构建 API 和 Web；开发命令同时监视三个工作区。

**数据库。** MongoDB 保存用户、问卷主体、不可变版本、填写会话和正式回答。题目、选项、校验和跳转嵌入版本快照；回答独立保存以支持无界增长和聚合。副本集事务处理跨文档原子操作，索引处理唯一性、TTL、分页与统计访问路径。

### 3.3 关键数据流

**编辑与发布。** 创建问卷时，事务预先生成问卷和 v1 版本 ID 并互相引用。草稿写入先读取整份版本、在内存中验证新状态，再以当前 revision 条件整体更新版本并同步问卷更新时间。发布事务重新执行结构、截止和跳转检查，条件更新版本状态及问卷指针；任一写入失败则整体回滚。

**填写与提交。** 公开摘要只返回白名单字段。登录用户创建会话后取得动态 Path 的填写 Cookie，会话固定发布版本。前端逐题计算路径并暂存答案；提交时 API 先验证双 Cookie 和幂等状态，再解析较大正文、重新计算真实路径、规范化路径内答案，并在事务中先占用会话后插入回答。

**统计读取。** 创建者明确选择一个已发布版本。服务先验证所有权和版本状态，再在快照事务中计算总数、到达、回答、选择和数字结果。文本答案及实名提交按索引分页，用户信息按一批 ID 查询，避免逐条读取。匿名响应经字段白名单和加密游标处理。

### 3.4 信任边界与部署

浏览器输入、`sessionStorage`、路径参数、游标和客户端计算结果都视为不可信。登录 Cookie 证明当前账号，填写 Cookie 证明对特定会话随机令牌的持有，两者同时通过后仍需按数据库中的 ownerKey 校验账号。客户端不接触 JWT 内容、填写令牌摘要、密钥或 MongoDB。

本地部署由 Vite、Express 和 Docker Compose 中的 MongoDB 组成。MongoDB 以 `rs0` 单节点副本集运行，宿主机通过 `directConnection=true` 连接。该拓扑用于课程开发与验收，不宣称具备生产高可用；生产环境还需要 HTTPS、可信代理配置、多节点数据库、共享限流、集中日志和独立密钥管理。

## 第 4 章 MongoDB 数据库设计

### 本章要点

- 五个集合采用“版本内嵌问卷定义、回答独立存储”的混合模型。
- 条件更新、事务和唯一索引共同维护发布、草稿和提交不变量。
- TTL 只负责延迟物理清理，业务到期由服务端时间即时判断。
- 聚合与索引结论由全新种子库、并发测试和 `explain()` 实验验证。

### 4.1 设计目标与原则

本系统的数据设计首先服务于“发布版本不可变、回答按版本隔离、多人并发填写和第二阶段增量扩展”四个目标。问卷定义在编辑期间会频繁修改，发布后又必须作为解释历史回答的稳定依据；回答数量会持续增长，并且多个填写者可能同时提交。因此，系统不能把所有业务数据放在一个无限增长的问卷文档中，也不适合把题目、选项和规则拆成大量必须反复关联查询的小集合。

最终采用五集合与版本内嵌相结合的混合模型：`users` 保存账号；`surveys` 保存问卷长期身份和当前指针；`survey_versions` 保存完整问卷快照，并在版本内嵌题目、选项、校验和跳转规则；`fill_sessions` 保存短期填写状态；`responses` 独立保存永久回答。该模型利用 MongoDB 文档适合保存聚合对象的特点，同时把无界增长、并发写入频繁的回答从问卷定义中分离。

设计过程中考虑并放弃了两种方案。第一种是把版本和全部回答都嵌入 `surveys`。它读取单份问卷方便，但回答数组会无界增长，多人提交会竞争同一文档，并可能触及 16 MiB 文档上限。第二种是按关系数据库思路把题目、选项、校验和每条跳转规则分别拆成集合。该方案会增加打开问卷、发布检查和历史版本读取所需的关联查询，也更难保证一次发布得到自包含的不可变快照。当前混合方案把有共同生命周期且总量有上限的问卷定义内嵌，把生命周期独立或数量无上限的数据拆分，符合本项目的访问模式。

### 4.2 集合关系与嵌套结构

**图 4-1 五个集合的关系与版本内嵌结构**

```text
users 1 ── N surveys 1 ── N survey_versions
                   │                  │
                   │                  ├── questions[]
                   │                  │    ├── validation
                   │                  │    ├── options[]
                   │                  │    └── jumpRules[]
                   │                  │
                   └── N fill_sessions N ── 1 survey_versions
                              │
                              └── 0..1 responses

survey_versions 1 ── N responses
users 1 ── N identified sessions/responses（仅实名模式直接引用）
```

`surveys.currentVersionId` 指向当前公开版本，`surveys.draftVersionId` 指向正在编辑的下一版本，两者都可以为空。首次创建后只有 v1 草稿；首次发布后只有当前版本；创建修改时，当前发布版本和下一版本草稿可以同时存在。填写会话与正式回答都保存 `surveyVersionId`，所以发布 v2 后，已经打开的 v1 会话和 v1 历史统计仍由 v1 的题目、规则与截止时间解释。

题目数组的位置是唯一顺序，不另存 `order`。题目、选项和规则使用稳定的 `questionId`、`optionId` 和 `ruleId`，复制到下一版本时保留，方便比较版本并让已有回答继续对应原题。版本发布后整份文档不可修改，因而嵌套内容不会出现题目已变而历史回答含义随之改变的问题。

### 4.3 users 集合

`users` 只保存认证所需信息，不承担问卷或回答的嵌套容器职责。

**表 4-1 users 集合字段**

| 字段                 | 类型     | 必填 | 作用与约束                               |
| -------------------- | -------- | ---- | ---------------------------------------- |
| `_id`                | ObjectId | 是   | 用户内部标识                             |
| `username`           | String   | 是   | 保留用户注册时的公开写法                 |
| `usernameNormalized` | String   | 是   | trim 后转小写的查询键，唯一索引          |
| `passwordHash`       | String   | 是   | 带参数与盐的 scrypt 记录，不保存明文密码 |
| `registeredAt`       | Date     | 是   | 注册时间                                 |

用户名唯一性以 `usernameNormalized` 为准，而不是 `username`。并发注册不依赖“先查再插”，最终由唯一索引裁决；后端只把该索引的重复键错误映射为 `USERNAME_TAKEN`。匿名填写不会在回答中直接引用用户 `_id`，避免创建者通过回答记录获得填写者身份。

### 4.4 surveys 集合

`surveys` 表示问卷跨版本不变的长期身份，只保存管理信息、公开入口和版本指针，不保存具体题目。

**表 4-2 surveys 集合字段**

| 字段               | 类型               | 必填 | 作用与约束                             |
| ------------------ | ------------------ | ---- | -------------------------------------- |
| `_id`              | ObjectId           | 是   | 问卷长期内部标识                       |
| `ownerId`          | ObjectId           | 是   | 创建者，所有创建者接口均按它隔离       |
| `publicId`         | String             | 是   | 至少 128 位随机值的 URL 安全编码，唯一 |
| `internalName`     | String             | 是   | 仅创建者可见的管理名称                 |
| `manualStatus`     | `open` 或 `closed` | 是   | 与版本状态分离的人工开关               |
| `currentVersionId` | ObjectId 或 null   | 是   | 当前公开版本指针                       |
| `draftVersionId`   | ObjectId 或 null   | 是   | 当前草稿指针                           |
| `createdAt`        | Date               | 是   | 创建时间                               |
| `updatedAt`        | Date               | 是   | 最近管理或草稿写入时间，参与列表排序   |

公开链接只依赖 `publicId`，发布新版本不会更换链接。`internalName` 与版本中的公开 `title` 分离，避免创建者整理列表时意外修改填写者看到的标题。手工关闭也不写入版本，因为关闭是问卷入口当前是否开放的运营状态；版本的内容、历史回答和统计仍需保留。

### 4.5 survey_versions 集合

`survey_versions` 是数据库设计的核心。每条文档保存一个完整、可独立解释的问卷版本。

**表 4-3 survey_versions 集合字段**

| 字段                       | 类型                        | 必填 | 作用与约束                            |
| -------------------------- | --------------------------- | ---- | ------------------------------------- |

| `surveyId`                 | ObjectId                    | 是   | 所属问卷                              |
| `versionNumber`            | Number                      | 是   | 从 1 开始递增，与 surveyId 组成唯一键 |
| `status`                   | `draft` 或 `published`      | 是   | 发布后不可通过草稿接口修改            |
| `revision`                 | Number                      | 是   | 草稿乐观并发版本号                    |
| `title`                    | String                      | 是   | 填写者看到的公开标题                  |
| `description`              | String                      | 是   | 问卷说明，可为空字符串                |
| `identityMode`             | `anonymous` 或 `identified` | 是   | 当前版本的身份展示方式                |
| `allowMultipleSubmissions` | Boolean                     | 是   | 是否允许同一 ownerKey 重复提交        |

### 4.6 fill_sessions 集合

`fill_sessions` 把一次填写固定到打开时的发布版本，并保存短期所有权、有效期和提交状态。

**表 4-4 fill_sessions 集合字段**

| 字段                          | 类型                         | 必填   | 作用与约束                          |
| ----------------------------- | ---------------------------- | ------ | ----------------------------------- |
| `_id`                         | ObjectId                     | 是     | 会话标识                            |
| `surveyId`、`surveyVersionId` | ObjectId                     | 是     | 固定问卷和打开时版本                |
| `identityMode`                | String                       | 是     | 会话创建时复制的身份模式            |
| `ownerKey`                    | String                       | 是     | 问卷内 HMAC 假名键                  |
| `userId`                      | ObjectId                     | 仅实名 | 匿名会话不保存该字段                |
| `sessionTokenHash`            | String                       | 是     | 填写 Cookie 中随机令牌的不可逆摘要  |
| `status`                      | active、expired 或 submitted | 是     | 会话状态                            |
| `activeSlot`                  | Number 或 null               | 是     | 活动时为 0–4，结束后释放            |
| `startedAt`、`expiresAt`      | Date                         | 是     | 会话开始与业务到期时间              |
| `purgeAt`                     | Date                         | 是     | 物理清理时间，等于 expiresAt 加七天 |
| `submittedAt`                 | Date 或 null                 | 是     | 成功提交时间                        |

业务有效期不能依赖 MongoDB TTL。TTL 后台线程不是精确定时器，而且会话到期后仍需短期保留记录以支持诊断和提交幂等。因此 `expiresAt` 用于每次业务请求的即时判断，`purgeAt` 才建立 TTL 索引并延后七天清理。活动槽位也通过 `expiresAt` 惰性释放，避免已经业务到期但尚未被 TTL 删除的文档继续占用名额。

### 4.7 responses 集合

`responses` 独立且永久保存正式提交。它不嵌入问卷或用户文档，以支持多人并发写入、分页、按版本聚合和长期历史保留。

**表 4-5 responses 集合字段**

| 字段                          | 类型     | 必填     | 作用与约束                                |
| ----------------------------- | -------- | -------- | ----------------------------------------- |
| `_id`                         | ObjectId | 是       | 正式回答标识                              |
| `surveyId`、`surveyVersionId` | ObjectId | 是       | 问卷与版本归属                            |
| `fillSessionId`               | ObjectId | 是       | 一次会话只能产生一份回答的唯一锚点        |
| `ownerKey`                    | String   | 是       | 内部所有权键，不向创建者返回              |
| `dedupKey`                    | String   | 条件必填 | 禁止重复时等于 ownerKey；允许重复时不写入 |
| `respondentId`                | ObjectId | 仅实名   | 匿名回答不保存该字段                      |
| `questionPath`                | String[] | 是       | 服务端计算的真实到达路径                  |
| `ignoredQuestionIds`          | String[] | 是       | 已提交但不在真实路径上的已知题目          |
| `answers`                     | Array    | 是       | 仅保存真实路径上的规范答案                |
| `submittedAt`                 | Date     | 是       | 正式提交时间                              |

`fillSessionId` 在会话 TTL 清理后允许悬空，因为正式回答的解释依赖 `surveyVersionId`，而不是依赖短期会话继续存在。禁止重复时，`dedupKey` 与 `surveyVersionId` 组成部分唯一索引；允许重复时不写 `dedupKey`，同一 ownerKey 可以产生多份回答。这样“是否允许重复”由数据本身决定，不需要用特殊空字符串绕过唯一索引。

### 4.9 事务、乐观并发与唯一约束

系统在跨文档不变量上使用 MongoDB 事务：创建问卷与 v1 草稿、保存草稿并同步列表更新时间、发布版本、创建或放弃下一版本草稿、修改题目或规则并同步更新时间，以及正式提交回答。所有相关数据库操作都显式传入同一 session，并使用 `withTransaction` 处理瞬时事务错误的自动重试。

事务不替代条件更新。草稿保存使用 `_id + surveyId + status: draft + revision` 作为写入条件，并在成功时把 revision 加一。两个客户端携带同一 revision 并发保存时，只能有一个条件更新成功；另一个请求重新读取后得到 `DRAFT_CONFLICT` 及当前 revision。发布同时要求版本仍为草稿、revision 未变化且问卷的 `draftVersionId` 仍指向它。正式提交先把未过期的 active 会话条件更新为 submitted 并释放槽位，再插入 response；失败时两步一起回滚。

唯一索引提供事务之外的最终不变量保护。例如两个事务并发创建下一版本草稿时，问卷指针条件与单草稿部分唯一索引共同保证只有一个成功；两个不同会话为禁止重复的版本并发提交时，`surveyVersionId + dedupKey` 部分唯一索引决定唯一胜者，失败事务不会留下已提交但没有回答的会话状态。

集成测试在创建问卷第二次插入后、发布版本状态修改后、问卷指针修改后、创建草稿版本插入后、提交会话状态修改后和回答插入后设置失败注入点，验证事务完全回滚。并发测试另外覆盖相同 revision 保存、发布与编辑竞争、发布与放弃竞争、并发创建草稿、同会话重试和两个会话竞争去重索引。

下面是发布事务的关键骨架，完整错误诊断和返回结构位于同一服务文件。

**代码 4-1 发布事务骨架，`apps/api/src/surveys/service.ts`**

```ts
published = await SurveyVersionModel.findOneAndUpdate(
  { _id: versionId, surveyId, status: "draft", revision },
  { $set: { status: "published", publishedAt: now, updatedAt: now } },
  { returnDocument: "after", session, timestamps: false },
);

const surveyWrite = await SurveyModel.updateOne(
```

### 4.10 匿名身份的数据层实现

匿名模式仍要求填写者登录，但登录只用于会话所有权和重复限制。服务端计算：

```text
ownerKey = HMAC-SHA256(
  ANONYMOUS_ID_SECRET,
  "survey-owner:v1\0" + surveyId + "\0" + userId
)
```

公式与实现中的固定域标签 `survey-owner:v1` 完全一致，且不包含版本 ID。因此同一账号在同一问卷的不同版本中得到相同 ownerKey，在不同问卷中不可直接关联。匿名会话不保存 `userId`，匿名回答不保存 `respondentId`；创建者接口也不返回 ownerKey、dedupKey、fillSessionId 或令牌摘要。

2026-10-21 在新建的本地 `survey_report_test` 种子库中按版本 `identityMode` 分组检查：4 个匿名会话的 `userId` 存在数为 0，3 份匿名回答的 `respondentId` 存在数为 0；2 个实名会话全部含 `userId`，2 份实名回答全部含 `respondentId`。检查后执行 `npm run seed:clean`，删除本轮生成的 3 个用户、3 份问卷、4 个版本、6 个会话和 5 份回答。

这是一种面向问卷创建者的假名化，不是绝对匿名。持有 `ANONYMOUS_ID_SECRET` 且能访问用户表的运维人员可以重新计算 ownerKey；直接轮换该密钥也会破坏历史会话所有权和去重。因此第一阶段不提供密钥轮换，未来需要增加 key version 和双读迁移。

### 4.11 文档体积与请求边界

嵌套模型必须控制数组上限。系统限制每个版本最多 100 道题，每个选择题最多 50 个选项，题目标题最多 300 个码点，选项文字最多 200 个码点。按 50 个最长选项估算，单题约 10,300 个码点；全部使用四字节字符时约 40 KiB，若 JSON 把非 BMP 字符转成两个 `\uXXXX`，最坏约 121 KiB，仍低于普通接口 256 KiB 请求体上限。100 道题的 BSON 正文最坏约 4 MiB，加字段开销后仍低于 MongoDB 16 MiB 单文档限制。

正式提交可能同时包含 100 道、每题 2,000 个码点的文本答案，按 JSON 最坏转义估算约 2.4 MB。接口解析顺序和 4 MiB 独立上限见 6.2 节；本节只据此确认请求体不会迫使问卷版本或回答文档突破 MongoDB 的 16 MiB 上限。

### 4.12 聚合与快照一致性

统计按 `surveyVersionId` 隔离，在一个 `readConcern: snapshot` 的只读事务中依次运行总数、路径到达、题目回答、选择项和数字摘要五条管道。每条管道职责单一，先匹配版本并尽早投影所需字段。测试在两条管道之间从事务外插入新回答，当前请求仍看到同一快照，并保持 `answeredCount ≤ reachedCount ≤ submissionCount`。

系统没有把全部指标放进单个 `$facet`。原因是 `$facet` 每个阶段生成的文档有 100 MB 上限且不能借助 `allowDiskUse` 落盘，最终聚合结果仍受 16 MiB BSON 限制。多条管道还便于分别设置 `maxTimeMS`、定位慢查询和编写职责明确的测试。`explain("executionStats")` 不能作为事务内聚合选项，因此实验在事务外复用同一批生产管道。

**代码 4-2 到达数聚合管道，`apps/api/src/statistics/pipelines.ts`**

```ts
reached: [
  match(),
  { $project: { questionPath: 1 } },
  { $unwind: "$questionPath" },
  { $group: { _id: "$questionPath", count: { $sum: 1 } } },
];
```

### 4.13 第二阶段扩展性

`schemaVersion`、稳定题目 ID 和不可变发布版本为第二阶段的数据迁移与兼容读取提供基础。新增题型或规则时可以提高 schemaVersion，让读取层同时支持旧结构和新结构，而不必修改历史发布版本或回答。

如果回答规模远超单机能力，可评估以 `surveyVersionId` 为前缀的复合分片键，使单版本统计和分页成为定向查询。但热门问卷可能形成单分片热点，现有唯一索引在分片集合中的约束也需要重新设计，因此本报告只把它列为候选方向，不声称当前系统已经支持分片。统计量继续增大时，还可以在不改变原始回答的前提下增加异步物化汇总；原始 `responses` 仍作为可重新计算和审计的事实来源。

## 第 5 章 跳转设计

### 本章要点

- 规则按数组顺序求值，第一条命中后立即跳转，否则进入下一题。
- 前后端复用同一纯函数计算路径，服务端提交时重新计算，不信任客户端路径。
- 发布检查采用精确默认边模型，循环阻止发布，不可达和遮蔽规则给出警告。
- 稳定的 questionId 和 ruleId 用于引用、错误定位和版本复制。

### 5.1 设计目标与规则模型

问卷跳转必须同时满足三个目标：填写时按确定规则前进、发布前能够发现循环等结构问题、前后端对同一答案得到完全相同的路径。为此，系统没有把跳转逻辑分散在 Vue 页面和 Express 路由中，而是在 `packages/survey-logic` 中实现无数据库依赖的纯函数，前端预览、填写路径、发布检查和后端正式提交共同调用。

每道题保存一个有序的 `jumpRules[]`。规则采用扁平结构：

```text
{ ruleId, operator, value, targetQuestionId }
```

`ruleId` 是跨草稿修改和版本复制保持稳定的定位标识；`operator` 表示判断方式；`value` 保存选项 ID、选项 ID 数组或数值；`targetQuestionId` 指向同版本中的目标问题。规则只引用稳定 ID，不引用数组下标，因此题目重排不会让引用指向错误对象，但重排可能把原来的向前跳转变成回跳，发布检查仍需重新构图。

不同题型允许的操作符如下表。文本题在第一阶段不支持跳转规则，避免引入模糊的字符串匹配语义。

**表 5-1 题型与跳转操作符**

| 来源题型 | 可用操作符                               | 规则值               |
| -------- | ---------------------------------------- | -------------------- |
| 单选题   | `equals`                                 | 一个来源题 optionId  |
| 多选题   | `contains`、`containsAll`、`containsAny` | 一个或一组 optionId  |
| 数字题   | `equals`、`gt`、`gte`、`lt`、`lte`       | 安全范围内的有限数值 |
| 文本题   | 无                                       | 只允许空规则数组     |

每题规则数量默认最多 20 条，由 `JUMP_RULE_MAX_PER_QUESTION` 配置，启动时强制校验为 1 至 100 的整数。多选规则数组不得重复、不得超过该题选项数，并由服务端按来源题的选项顺序规范化后存储，使语义相同的输入获得稳定表示。

### 5.2 保存时校验与引用保护

跳转规则整组保存，而不是逐条 PATCH。客户端提交 `revision` 与完整 `rules`，服务端先校验字段白名单、ID 格式、操作符和值的原始类型，再读取问卷和草稿，依次确认所有权、草稿状态及 revision。来源题不存在返回 `QUESTION_NOT_FOUND`；目标题不存在、目标题等于来源题、条件选项不属于来源题或规则值不符合题型时，返回 `VALIDATION_ERROR`，并用 `details.path` 指向具体的 `rules[i]` 字段。

自跳转在保存时直接拒绝，因为任何重排都不可能让目标与来源成为同一题。指向更靠前题目的规则可以暂存在草稿中：创建者可能稍后重排题目，过早删除规则会造成数据损失；但只要它最终形成循环，发布闸门就会阻止发布。新增规则由服务端生成全版本唯一的 `ruleId`；修改时只接受来源题原有的规则 ID，伪造、重复或借用其他题的 ID 均被拒绝。

题目和选项删除还要检查反向引用。若某题被任一规则作为目标，删除题目返回 `QUESTION_REFERENCED`；若要删除的选项仍被来源题规则使用，返回 `OPTION_REFERENCED`。错误详情给出稳定的 questionId 和 ruleId 列表，前端可以把用户定位到引用位置。题目内容 PATCH 会保留原有 `jumpRules`，不会因为编辑标题或校验条件意外清空分支。

规则保存沿用草稿的乐观并发控制：服务端在内存构造完整新数组，再以 `status: draft + revision` 条件整体更新并把 revision 加一，同时在同一事务刷新问卷列表的 `updatedAt`。因此两个携带相同 revision 的并发保存只能有一个成功。

### 5.3 填写时的确定性求值

`evaluateNextQuestion(questions, currentQuestionId, answer)` 遵循“第一条命中优先”。它从上到下检查当前题规则，首条匹配后立即返回目标题；没有规则命中时进入题目数组中的下一题，最后一题则结束。规则顺序本身就是业务语义，因此编辑器显示并保存明确顺序。

未回答不匹配任何规则，包括数字题的 `lt` 和 `lte`，而是直接走默认边。路由函数只接受规范形态：单选必须是该题 optionId 字符串，多选必须是无重复且全部属于该题的 optionId 数组，数字必须是安全范围内的有限数值。数字字符串 `"5"`、未知选项或重复多选不会被隐式转换，也不会让路径计算抛异常，而是按未回答处理。

这一点不等于放过无效答案。正式提交先用规范形态计算路径，再用第 6 章的 `validateAnswer` 对真实路径中的答案做完整校验；类型错误最终仍会被拒绝。把“路由是否能安全继续”和“答案能否正式提交”分开，可以确保异常客户端数据不会让路径函数崩溃，同时不降低提交约束。

`computePath` 从第一题开始反复调用上述函数，并维护已访问 questionId 集合。如果再次访问已有题目，函数返回包含重复点的失败结果而不是死循环。填写页的“上一题”依据已经走过的实际路径回退，而不是简单地把数组下标减一；答案变化后，后续路径会重新计算。

下面的核心节选省略了类型声明和空问卷分支，保留了两个函数的实际控制流。

**代码 5-1 路由与路径循环保护，`packages/survey-logic/src/index.ts`**

```ts
const matched = question.jumpRules.find((rule) => matches(rule, answer));
if (matched) return { kind: "question", questionId: matched.targetQuestionId };
const next = questions[index + 1];
return next
  ? { kind: "question", questionId: next.questionId }
  : { kind: "end" };

while (true) {
  if (seen.has(current))
    return { ok: false, questionIds: path, repeatedQuestionId: current };
  seen.add(current);
  path.push(current);
  const next = evaluateNextQuestion(questions, current, answers[current]);
  if (next.kind === "end") return { ok: true, questionIds: path };
  current = next.questionId;
}
```

### 5.4 发布检查的精确图模型

发布检查把问题视为顶点，把可能发生的跳转视为有向边。每条合法规则产生一条规则边。默认的“进入下一题”边并非无条件存在，否则从第一题沿默认边总能到达全部题目，`QUESTION_UNREACHABLE` 将永远无法触发。

系统采用以下精确边界：当来源题是必答单选题，且 `equals` 规则覆盖其全部选项时，填写者必然命中某条规则，因此不画默认边；其他情况，包括非必答、未完全覆盖的单选、多选和数字题，都保守地保留到下一题的默认边。该模型不试图求解数字区间是否穷尽等复杂条件，换取可解释且不会误报“不可达”的安全边界。

例如，Q1 是必答单选，A 和 B 两个选项都跳到 Q3。Q1 的默认边被移除，图中 Q2 从第一题不可达，因此得到警告。

**图 5-1 必答单选覆盖全部选项时的不可达题**

```text
Q1 --A/B--> Q3 --> 结束
Q2 --默认--> Q3       （Q2 不可达）
```

循环报告不能依赖一次 DFS 的遍历顺序。默认边只会向数组后方移动，所以任一环必然至少包含一条目标不晚于来源的规则边，即目标是来源自身或更靠前的题。发布检查先把自跳转作为 `INVALID_STRUCTURE` 报告；对其余向后规则，逐条确认来源题从第一题可达且目标能够回到来源，再用 BFS 求经过该规则的最短回路。结果把稳定的 `questionIds`、questionId、ruleId 和 path 放入 `JUMP_CYCLE`。这样即使 DFS 首先遇到的是一条没有 ruleId 的默认回边，最终报告仍能准确指向应修改的规则。

发布检查还给出两类非阻止警告：从第一题无法到达的题为 `QUESTION_UNREACHABLE`；同一题中与更早规则具有相同操作符和值的后续规则为 `SHADOWED_RULE`。数组型条件按集合语义识别重复，警告消息指出遮蔽它的规则位置。错误与警告都按题目顺序、规则顺序稳定排序，前端不依赖可能变化的数组下标，而用稳定 ID 定位。

### 5.5 发布闸门与运行时防御

草稿检查接口是只读操作，不增加 revision。结果包含被检查的 revision、`valid`、`errors` 和 `warnings`。空问卷、截止时间已过、结构损坏和跳转循环属于阻止项；不可达题和重复规则属于警告。发布时不能信任先前检查结果，而是在发布事务内对相同快照再次调用 `validateForPublish`。有错误返回 `PUBLISH_BLOCKED`；只有警告时必须显式提交 `acknowledgeWarnings: true`，且 revision 一旦变化便需要重新检查和确认。

发布检查还防御性核验题目、选项和规则 ID 的全局唯一性，题数、选项数和规则数上限，目标题存在性及选项归属。正常写接口已经阻止这些损坏，但发布是不可逆边界，因此不能假设数据库中的旧数据或测试构造始终合法。正式提交也对绑定的发布版本重新执行结构检查；若检测到损坏或路径循环，返回 `SURVEY_VERSION_INVALID` 并记录服务端日志，不尝试猜测填写路径。

### 5.6 测试证据

本章证据对应追踪矩阵 JUMP-01～04 和 PUBLISH-01。第 9 章以场景卡记录操作符矩阵、默认边、循环与不可达、规则并发保存和发布阻止的输入、预期与结果；固定种子的惰性路径枚举用于对拍静态图与实际路径。

## 第 6 章 校验设计

### 本章要点

- HTTP、题目定义、发布和正式提交分别承担不同层次的校验责任。
- 缺省校验值在写入时补全，已发布版本不会随程序默认值变化。
- 文本使用 Unicode 规范化和码点计数，答案以稳定形态存入数据库。
- 服务端重新计算真实路径，并一次返回路径内全部答案问题。

### 6.1 分层校验原则

系统把“校验”拆成四层，而不是依赖 Mongoose 自动转换或浏览器控件：HTTP 边界校验负责来源、媒体类型、体积和 JSON 语法；题目定义校验负责把草稿写成完整规范结构；发布校验负责不可逆前的整份防御性复核；提交校验负责按服务端真实路径检查答案。各层失败位置不同，错误码和可恢复方式也不同。

请求中出现未知字段一律拒绝，不做静默忽略。对象 ID、questionId 等先检查格式，再检查资源和所有权。题目写操作的顺序固定为：请求形态 400 → 问卷或版本 404 → 非草稿 409 → revision 冲突 409 → 来源题不存在 404 → 业务规则失败。该顺序使同一请求同时存在多个问题时仍返回稳定结果，测试不依赖偶然的中间件或查询顺序。

### 6.2 HTTP 与安全边界校验

所有有请求体的接口必须使用 `application/json`，只有无正文的退出接口豁免；畸形 JSON 返回 `VALIDATION_ERROR`，普通接口正文超过 256 KiB 返回 `PAYLOAD_TOO_LARGE`。所有 POST、PUT、PATCH、DELETE 及预检请求还要校验 `Origin` 与 `WEB_ORIGIN` 完全一致，不在允许来源内返回 `ORIGIN_NOT_ALLOWED`。CORS 虽允许凭据和必要方法，但不是 CSRF 的唯一防线。

全局正文解析器刻意绕过正式提交路径。该路由先认证登录 Cookie、验证填写 Cookie 和 ownerKey、处理已提交幂等及会话状态，然后才启用 4 MiB JSON 解析器。这样未认证的大请求先得到 401 或 404，不会让服务器预先缓冲数兆字节数据。提交正文只允许 `{ answers }`，最多 100 项；每项只允许 questionId 和 value，value 只能是字符串、有限数值、最多 50 项的字符串数组或 null。未知、重复或格式错误的 questionId 在业务路径计算前返回 `VALIDATION_ERROR`。

### 6.3 题目定义的规范化保存

新增题目需要 type、title、validation、options 和 revision，required 缺省为 false；替换题目是完整替换语义，必须提交 title、required、validation 和完整 options，但禁止提交 type、questionId 和 jumpRules。`validation` 必须存在，可以是空对象；服务端在保存前补齐所有缺省值并把规范形式写入 MongoDB，避免未来修改程序默认值时悄悄改变历史版本语义。

**表 6-1 四种题型的规范校验结构**

| 题型 | 规范校验结构与边界                                                              |
| ---- | ------------------------------------------------------------------------------- |
| 单选 | `{}`；选项 2–50 个                                                              |
| 多选 | `{ minSelections, maxSelections }`；缺省 1 和选项数，满足 `1 ≤ min ≤ max ≤ n`   |
| 文本 | `{ minLength, maxLength, digitsOnly }`；缺省 0、2000、false，且 `min ≤ max`     |
| 数字 | `{ integerOnly, minValue, maxValue }`；缺省 false、null、null，范围不超安全整数 |

若 `integerOnly` 为 true，数值上下限也必须为整数。`-0` 在保存时规范化为 `0`。选择题外的题型不能携带 options；选择题选项文字去除首尾空白后不得为空或重复，比较区分大小写。

名称、标题、说明和选项先执行 NFC 规范化，再做 trim、码点计数和比较。系统拒绝 Unicode `Cc` 控制字符，以及 U+202A–U+202E、U+2066–U+2069 双向控制符；说明字段单独允许正常换行。ZWJ 被保留，因此家庭、职业等组合 emoji 不会被拆坏。长度使用 `Array.from(text).length` 统计 Unicode 码点，而不是使用 JavaScript UTF-16 `length` 或 HTML `maxlength`。这些规则同样防止视觉等价的组合与分解字符绕过选项重复校验。

### 6.4 答案形态、规范化与错误码

`validateAnswer(question, candidate)` 返回规范化结果而不是简单布尔值。成功形态为 `{ ok: true, value, answered }`；失败形态为 `{ ok: false, code, path, reason }`。因此填写端提示、正式提交和后续统计都复用同一语义，不需要再次猜测 trim、多选排序或 `-0` 的处理。

**表 6-2 答案形态与规范化规则**

| 题型 | 已回答的输入形态           | 未回答                        | 规范化及主要约束                         |
| ---- | -------------------------- | ----------------------------- | ---------------------------------------- |
| 单选 | optionId 字符串            | 缺失或 null                   | 必须属于本题                             |
| 多选 | optionId 数组              | 缺失、null 或空数组           | 去重检查、数量边界，按题目选项顺序保存   |
| 文本 | 字符串                     | 缺失、null 或 trim 后空字符串 | NFC、trim、码点长度；digitsOnly 仅 ASCII |
| 数字 | 安全范围内的有限 JSON 数值 | 缺失或 null                   | 不接收字符串；`-0` 变 `0`                |

必答题未回答产生 `REQUIRED`；非必答题未回答返回 `answered: false` 并跳过其余校验。文本保留中间换行，只去首尾空白；`digitsOnly` 只允许 ASCII `0`–`9`，全角数字和阿拉伯—印度数字都失败。数值必须有限且绝对值不超过 `2^53−1`，再检查整数和上下限。答案错误使用稳定机器码：`TYPE_MISMATCH`、`UNKNOWN_OPTION`、`DUPLICATE_SELECTION`、`SELECTION_COUNT`、`TOO_SHORT`、`TOO_LONG`、`DIGITS_ONLY`、`OUT_OF_RANGE` 和 `NOT_INTEGER`。

**代码 6-1 文本答案规范化节选，`packages/survey-logic/src/index.ts`**

该片段位于空字符串和必答判断之后，展示长度与 ASCII 数字校验。

```ts
const value = candidate.normalize("NFC").trim();
const validation = question.validation as Extract<
  QuestionValidation,
  { minLength: number }
>;
const length = Array.from(value).length;
if (length < validation.minLength)
  return failure("TOO_SHORT", "文本长度小于最小值");
if (length > validation.maxLength)
  return failure("TOO_LONG", "文本长度超过最大值");
if (validation.digitsOnly && !/^[0-9]+$/.test(value))
  return failure("DIGITS_ONLY", "只能输入 ASCII 数字");
return { ok: true, value, answered: true };
```

### 6.5 服务端路径重算与批量错误返回

客户端不能决定自己“经过了哪些题”。提交服务从发布版本第一题开始，以客户端提供的候选答案重新计算真实路径。对于真实路径内的每题，调用 `validateAnswer` 并按路径顺序收集问题；错误一次返回且最多 100 项，每项包含 questionId、机器码 code、原提交数组中的 path 和中文 message。必答题完全未提交时没有数组下标，因此 path 为空字符串，前端仍可依靠 questionId 回到第一道错误题。

已知但不在真实路径上的答案被忽略，其内容不做业务校验，并记录到 `ignoredQuestionIds`。这样用户先填写后因修改前题答案改变分支时，不会因为旧分支残留而无法提交。该例外不适用于结构攻击：路径外 questionId 仍必须存在，外层 value 仍必须属于允许的 JSON 形态；未知题目、重复 ID 和对象等非法值在结构预检中直接拒绝。

最终只有路径内且 `answered: true` 的规范答案进入 `responses.answers`，同时保存服务端计算的 `questionPath`。这使统计不必重新猜测旧客户端当时采用的路径，也保证文本、数值和多选在库中都有稳定表示。

### 6.6 发布校验与答案校验的职责边界

题目定义校验回答“这道题的配置是否合法”，例如多选最小值是否大于最大值；答案校验回答“某个填写值是否符合已发布配置”。跳转规则合法性只依赖来源题型和选项归属，不依赖数字题的 minValue、maxValue 或 integerOnly：规则 `equals 2.5` 即使对当前整数题永远不命中，也不会让已保存结构失效。第一阶段可把这类情况扩展为提示，但不把它当成阻止保存的错误。

发布检查对整份版本再次验证 ID、目标、数量和图结构，防止绕过单题接口的损坏数据进入不可变状态。若提交时发现已经发布的数据仍损坏，系统不返回普通答案错误，而是使用 `SURVEY_VERSION_INVALID` 并记录日志。这一区分避免把系统数据问题误导为填写者输入问题。

### 6.7 测试证据

本章证据对应追踪矩阵 SEC-01、QUESTION-01～05、ANSWER-01 和 SUBMIT-01～03。第 9 章按场景卡记录 Unicode 边界、四题型缺省值、请求体积、路径外答案、稳定 issues 和最大合法提交等测试的输入与结果。

## 第 7 章 其他后端逻辑

### 本章要点

- 账号认证使用固定两小时 JWT 和参数受限的 scrypt，不提供滑动刷新。
- 发布版本不可变；下一版本草稿、关闭和到期组成明确的生命周期。
- 双 Cookie 会话把账号权限与一次填写令牌分开验证。
- 正式提交支持幂等重试，统计按发布版本隔离并限制匿名输出。

### 7.1 账号认证与密码安全

用户名只允许 3–20 位英文、数字和下划线。服务端 trim 后保留原始写法，同时生成小写 `usernameNormalized`；唯一性最终由数据库唯一索引保证，并发注册重复键只在 `keyPattern.usernameNormalized` 匹配时映射为 `USERNAME_TAKEN`。登录查询严格要求字符串，因此 `{ "$ne": null }` 等 NoSQL 注入对象在校验层即被拒绝。

密码注册长度为 10–128 个 Unicode 码点，要求同时包含英文字母和数字，且不能与规范化用户名相同。哈希前执行 NFKC，使用 Node 内置 `crypto.scrypt`，生产参数为 `N=2^15, r=8, p=3`、16 字节随机盐和 64 字节派生键，并显式设置 64 MiB maxmem。选择内置 scrypt 可以避免原生扩展安装差异，同时让哈希记录自带算法、参数、盐和派生值。验证严格限制记录参数、Base64URL 和字节长度；畸形记录或 `timingSafeEqual` 长度风险统一按失败处理。

用户名不存在时仍对一条预先生成、参数相同的假哈希执行 scrypt，登录只返回统一的 `INVALID_CREDENTIALS`，降低通过响应耗时枚举账号的风险。注册按 IP 限流；登录同时按 IP 总量和“IP + 规范化用户名”限流，以兼顾暴力猜测和密码喷洒。当前固定窗口计数保存在进程内，具有过期清理和容量上限，但多实例部署时不能共享，这是第一阶段已知边界。

登录令牌采用仅含 sub、iat、exp、iss 和 aud 的 HS256 JWT，固定有效期两小时，不放入可能过期的 username，也不提供滑动刷新。验证明确拒绝其他算法、错误签名、过期时间、错误签发者或受众；即使令牌签名有效，用户已经删除时仍返回 `AUTH_INVALID`。令牌存入 `survey_session` HttpOnly、SameSite=Lax Cookie，生产环境增加 Secure。JWT 密钥和匿名密钥启动时都必须至少 32 字符、不能是示例值且不能相同，否则服务拒绝启动。

### 7.2 版本生命周期与有效状态

问卷创建时在事务中同时生成 `surveys` 和 v1 草稿。草稿编辑使用单一 revision；每次设置、题目、排序或规则写入成功都把它加一。发布版本不可修改，修改需求通过当前版本深复制出下一版本草稿完成。复制使用字段白名单和 `structuredClone`，保留题目、选项和规则稳定 ID，但不复制数据库 `_id`、状态、revision、发布时间和时间戳。

发布是两步操作：先检查，再显式确认警告。发布事务重新检查当前草稿，成功后把它设为 published，并更新问卷的当前和草稿指针；并发条件与回滚机制见 4.9 节和代码 4-1。发布不增加 revision，也不改变 `manualStatus`。

`computeSurveyStatus` 统一有效状态：没有当前版本为 draft；手工关闭优先得到 closed；当前版本 deadline 小于等于服务端 now 时为 expired；否则为 published。关闭与自动到期不是同一持久状态：重新开放只改变 manualStatus，不能绕过已经过去的版本截止时间。状态函数由创建者列表、公开摘要和会话流程共用，并通过注入时钟测试边界。

系统保留完整版本历史。只有当前发布版本对新填写者开放，但旧会话仍绑定打开时的旧版本，旧回答统计也只与原版本组合。下一版本草稿可以放弃，初始 v1 草稿则不能删除；问卷本身的删除和归档有意留在第一阶段范围之外。

**图 7-1 问卷版本生命周期状态图**

```text
创建问卷 → v1 草稿 → 发布 v1 ───────────────→ 当前 v1
                         │                       │
                         ├─ 手工关闭 ↔ 重新开放  ├─ 创建 v2 草稿 → 放弃
                         │                       │
                         └─ 截止时间到达         └─ 发布 v2 → 当前 v2
```

`closed` 是问卷级人工状态，`expired` 由当前版本截止时间计算；两者都不会改写已发布版本或删除历史回答。

### 7.3 填写会话、双 Cookie 与问卷内匿名

公开摘要无需登录，开始填写必须登录。创建会话时不刷新两小时登录 Cookie，避免把固定到期变成可无限续期；登录过期后，填写者可以重新登录同一账号，再用尚未到期的填写 Cookie 恢复。登录返回路径只接受严格的站内 `/fill/...` 白名单，阻止开放重定向。

每个会话生成 256 位随机填写令牌，数据库只保存 SHA-256 摘要；原令牌放入名为 `survey_fill` 的 HttpOnly Cookie，Path 精确限制为该 session API 路径，SameSite=Lax，生产增加 Secure。恢复和提交必须同时通过登录 Cookie、填写 Cookie、sessionId、令牌摘要以及重新计算的 ownerKey，任何缺失或账号不匹配统一返回 `SESSION_NOT_FOUND`，不泄露会话是否存在。退出登录只清除登录 Cookie；填写页明确提示本地草稿仍在，但换账号无法取得会话所有权。

问卷内 ownerKey 的公式、字段不变量和威胁边界见 4.10 节。本节只使用该结果完成双 Cookie 所有权校验和版本内重复判断，不再重复保存匿名账号身份。

会话固定到创建时的 surveyVersionId，默认持续 30 分钟。`computeSessionState` 的优先级是已提交 → 显式过期 → 手工关闭 → 会话绑定版本截止 → 会话自身到期 → active，因此 v3 无截止时间也不能让已到期的 v2 会话恢复。每账号每问卷最多五个 activeSlot；创建前会惰性把业务已过期会话标记为 expired 并释放槽位，TTL 只在七天后清理文档。

### 7.4 正式提交、重复限制与幂等

提交路由采用“先认证，后大正文”的中间件顺序。通过双 Cookie 所有权后，若会话已经 submitted，则不比较本次重试正文，也不再检查关闭、版本截止或会话到期，直接返回第一次保存的回答编号并清除填写 Cookie。这样客户端在成功响应丢失后，即使跨过第 30 分钟或问卷随后关闭，仍能得到稳定幂等结果。

新提交先在服务端重算路径并规范化答案，再执行 4.9 节说明的提交事务。两个同会话并发请求最终收敛到同一 response；`fillSessionId` 唯一索引是最后兜底。

**图 7-2 正式提交事务时序图**

```text
浏览器 → API：登录 Cookie + 填写 Cookie + answers
API → fill_sessions：验证所有权及已提交幂等
API → 共享逻辑：重算 questionPath 并规范化路径内答案
API → MongoDB 事务：active 会话改为 submitted，释放 activeSlot
API → MongoDB 事务：插入 response；任一步失败则整体回滚
API → 浏览器：201 或幂等 200，并按原 Path 清除填写 Cookie
```

禁止重复的版本在 response 写入 `dedupKey=ownerKey`，由 `{ surveyVersionId, dedupKey }` 部分唯一索引实现“每账号每版本一次”；允许重复时不写 dedupKey。创建会话时也先查已有正式回答，尽早返回 `ALREADY_SUBMITTED`，但并发正确性仍依赖提交事务和唯一索引。不同版本使用不同 surveyVersionId，因此同一账号可以各提交一次。

客户端答案草稿只存入 `sessionStorage`，不含 Cookie 或其他凭据。恢复时把本地数据视为不可信：限制体积、丢弃未知题目和错误类型，重新运行答案校验与路径计算；会话所有权失败后立即删除对应草稿。自动保存使用防抖并捕获浏览器存储配额错误。该方案降低意外关闭页面造成的数据损失，但共用电脑、浏览器扩展和本地 XSS 仍是已知边界。

### 7.5 按版本统计与隐私输出

统计只允许问卷所有者查看 published 版本，草稿返回 `VERSION_NOT_PUBLISHED`。所有聚合以 surveyVersionId 为范围，在同一 snapshot 事务中计算总提交、到达、回答、选项和数字摘要；每条管道设置 maxTimeMS，超时或瞬时事务不可用统一返回 `STATISTICS_UNAVAILABLE`。接口按用户限流，响应使用 `Cache-Control: no-store`。

统计结果满足 `answeredCount ≤ reachedCount ≤ submissionCount`。单选选项人数和等于 answeredCount，多选每个选项人数不超过 answeredCount，数字 count 等于 answeredCount；生产发现破坏时只记录聚合日志，不把潜在数据损坏伪装成普通零值。数字题无数据时 average、minimum 和 maximum 返回 null。界面把 `notReachedCount` 明确标为“未到达（被跳转跳过）”，与到达但未回答分开。

文本回答分页先在首个 `$match` 中限定版本、questionId 和游标范围，沿 `{ surveyVersionId, submittedAt, _id }` 索引排序并 limit+1，最后才从 answers 数组投影目标答案。实名版本一次 `$in` 批量查询用户，避免 N+1，并额外提供全部实名提交记录，即使某份提交没有文本答案也能看到填写者。匿名版本不返回 respondentId、精确 submittedAt、responseId、ownerKey 或 dedupKey，只显示 UTC 日期。

匿名文本和实名提交分页游标使用 AES-256-GCM，而不是可读的签名 Base64URL。密钥从 JWT_SECRET 和专用域标签派生，随机 IV、AAD 与认证标签同时保证机密性和完整性，游标还绑定接口 kind、问卷、版本和题目。这样创建者不能通过解码游标取得精确提交时间或带时间戳的 ObjectId。匿名仍存在页内相对顺序、小样本内容和极值推断风险，界面与报告必须如实说明。

### 7.6 统一错误、限流与可观察性

所有 API 错误返回 `{ error: { code, message, details? } }`，未知 API 路径也返回 JSON `NOT_FOUND`，不会落入 Express 默认 HTML。400 用于请求结构和答案校验，401 用于认证，403 用于来源，404 同时承担资源不存在和防越权枚举，409 表示资源当前状态冲突，413/415 处理正文边界，429 携带 Retry-After，统计超时使用 503，未预期异常才使用 500。

限流阈值全部由环境变量配置并在启动时校验；认证、问卷写、创建填写会话、正式提交和统计分别计数。固定窗口存储会清理过期键并限制容量，但它只适合单进程课程部署；生产多实例应迁移到 Redis 等共享存储并谨慎设置 `trust proxy`。同样，JWT 在第一阶段没有服务端撤销列表，主动退出只清除浏览器 Cookie，已泄露令牌理论上可用到两小时到期。

后端只在未预期错误、发布版本结构损坏、会话引用断裂和统计不变量破坏时记录必要日志，不输出密码、Cookie、ownerKey、令牌或回答正文。健康检查对数据库执行带两秒超时的 ping，而不是只读取 Mongoose 被动 readyState；数据库不可响应时 API 仍存活并返回 degraded，便于区分进程故障与依赖故障。

### 7.7 本章测试证据

本章证据对应追踪矩阵 AUTH-01～05、SEC-01～02、VERSION-01～04、FILL-01～07、SUBMIT-04～07 和 STATS-01～07。第 9 章按场景卡记录认证攻击面、版本竞争、双 Cookie、提交幂等、匿名字段扫描、快照一致性和 50,000 份回答实验。

## 第 8 章 API 与前端实现

### 本章要点

- 29 条路由按认证、创建者管理、公开填写和统计查询分组，统一使用 JSON 错误结构。
- 前端通过相对 `/api` 路径访问 Vite 代理，Cookie 由浏览器管理，不把凭据写入 Web Storage。
- 创建者工作台把版本、设置、题目、跳转、预览发布和统计分区呈现，并共享同一个 revision 写入锁。
- 填写页按服务端计算规则逐题前进，支持安全草稿恢复、答案复核、错误定位和账号切换。

### 8.1 API 分层与接口分组

Express 应用先执行 Origin、CORS、Content-Type 和正文解析边界，再进入业务路由。认证中间件只负责确认当前账号；资源所有权、版本状态、revision 和业务不变量由服务层判断。路由层因此保持较薄，只进行路径与请求形态解析、限流计数和 HTTP 状态映射。完整字段、响应示例和错误判定顺序收录在 `docs/API.md`，正文按职责概括实际实现的 29 条路由。

**表 8-1 API 路由分组**

| 分组     | 数量 | 主要路径与职责                                              | 鉴权                                |
| -------- | ---: | ----------------------------------------------------------- | ----------------------------------- |
| 健康检查 |    1 | `GET /api/health`，区分 API 与数据库状态                    | 无                                  |
| 账号     |    4 | `/api/auth` 下的注册、登录、当前用户和退出                  | 按接口                              |
| 问卷管理 |   17 | `/api/surveys` 下的列表、草稿、题目、规则、发布、状态和历史 | 创建者登录                          |
| 公开填写 |    4 | `/api/public` 下的公开摘要、创建或恢复会话、正式提交        | 摘要公开，其余登录并校验填写 Cookie |
| 统计读取 |    3 | 版本统计、文本回答分页和实名提交记录                        | 问卷所有者                          |

公开接口不直接复用创建者版本响应。填写者只收到标题、说明、身份模式、截止时间、题目和规则等完成问卷所需字段，不收到 revision、内部 surveyId、ownerKey 或时间戳。创建者统计也按白名单输出；匿名版本进一步隐藏响应 ID、账号和精确提交时间。

### 8.2 HTTP 状态、错误与游标

所有失败响应采用 `{ error: { code, message, details? } }`。400 表示请求结构或答案校验失败；401 表示缺少或失效登录；403 表示来源不允许；404 同时用于不存在和越权隐藏；409 表示版本、发布、会话或重复提交冲突；413、415、429 和 503 分别表示正文过大、媒体类型错误、限流及统计暂不可用。未知 API 路由也返回 JSON `NOT_FOUND`，不落入 Express 的 HTML 404。

字段错误使用稳定的 `details.path`，前端可把截止时间、题目或选项错误显示在对应控件附近。答案问题使用 questionId、机器码、path 和 message，并按真实填写路径排序。`DRAFT_CONFLICT` 返回当前 revision，前端提示刷新，而不是覆盖其他页面已经保存的内容。

问卷和版本列表使用带 HMAC 签名的 Base64URL 游标，因为内容属于创建者自己的资源；匿名文本与实名提交分页使用 AES-256-GCM 加密游标，防止精确提交时间和 ObjectId 从载荷中泄露。所有游标绑定接口 kind 和资源范围，格式错误、跨接口复用或篡改统一返回 `VALIDATION_ERROR`。

### 8.3 创建者工作台

Vue 前端以 `App.vue` 维护登录、问卷列表和当前版本的顶层状态，并把截止时间、题目、跳转、已发布只读内容与统计拆成独立组件。问卷列表显示内部管理名称、草稿或当前版本及有效状态；编辑页侧边导航可直接定位版本历史、管理名称、基础设置、每道题、跳转和发布区域，窄屏时调整为适合纵向浏览的布局。

草稿页面只有一个 revision 来源。保存设置、题目、排序或规则期间，全部写按钮共同禁用；成功后统一采用响应的新 revision，清除旧发布检查结果。题目卡片逐张保存，未完成的新卡片留在前端内存，不会因为其他卡片保存而被丢弃。发送题目请求时按白名单构造正文，避免把响应中的只读 `questionId`、`type` 或 `jumpRules` 展开回传。

发布区按“检查能否发布 → 预览 → 确认发布”排列。错误阻止预览；警告需要二次确认，并天然绑定被检查的 revision。发布后页面切换为只读版本，仍完整显示题目、校验和跳转；修改需求通过当前版本创建下一草稿。统计面板始终绑定用户选择的发布版本，不把不同版本回答合并。

### 8.4 填写页与会话恢复

公开链接为 `/fill/:publicId`。摘要可以匿名读取，但开始填写必须登录；页面在按钮前说明匿名或实名边界，并显示当前账号、退出登录和切换账号入口。登录返回地址只接受预定的站内填写路径。创建会话后地址包含 sessionId，浏览器同时持有登录 Cookie 和 Path 受限的填写 Cookie。

填写页使用共享函数计算当前路径，显示“第 n 题（最多 N 题）”；上一题按实际走过的路径返回。每次前进先在本地运行答案校验，提交前提供复核页；服务端返回批量 issues 时，页面回到第一道错误题并在控件附近显示原因。倒计时以服务端 `serverNow` 和 `performance.now()` 的经过时间计算，最终有效性仍由服务端时钟判定。

非凭据答案经防抖写入 `sessionStorage`，键包含问卷、版本和会话。刷新时先恢复服务器会话，再把本地草稿视为不可信输入：限制体积，丢弃未知题目和错误类型，并重新计算答案与路径。换账号导致所有权校验失败时立即删除该会话草稿；主动退出活动会话前先保存草稿并说明同账号可以继续、其他账号不能恢复。

### 8.5 表单反馈与界面边界

截止时间输入把年份和分钟保留为手工输入，月、日、小时和时区使用同一区域内的滚动选择；无时区或无效日期的错误显示在控件下方。登录和注册密码框提供带无障碍标签的显隐按钮。名称、标题、说明和回答均使用普通文本插值，不使用 `v-html`。

页面离开、退出或切换版本前检查未保存内容。成功消息和发布错误在退出登录时清空，避免跨账号保留旧状态。发布版本只读、草稿预览、实名提交记录和匿名信息边界均有组件或请求测试；桌面和半屏布局另经过人工检查。

## 第 10 章 AI 使用过程

### 本章要点

- AI 参与需求整理、候选设计、编码、测试、文档和问题诊断，但每个里程碑均由项目负责人决定是否采用并完成浏览器验收。
- 最初一次性生成全项目的方式被人工否决，之后改为“讨论、定稿、实现、自动检查、人工验收”的阶段流程。
- 设计审阅多次发现 AI 候选中的安全、并发和隐私缺口；修改内容与实际提交、测试和日志相互对应。
- 提示词日志随开发记录，不在报告阶段补写未发生的对话，也不保存密钥、Cookie 或种子密码。

### 10.1 工具分工与责任边界

项目使用 Codex 读取本地作业要求和仓库、提出候选方案、修改代码与文档、运行终端检查并整理实验。项目负责人负责业务取舍、逐轮审阅、启动和操作浏览器、提供现场现象以及决定是否通过。设计阶段还采用独立审阅意见检查候选方案的歧义、数据库约束、安全边界和跨文档一致性；这些意见只有在项目负责人明确确认后才进入设计。

Docker、MongoDB、Vitest、TypeScript 编译器和 Git 不属于生成式 AI，但它们提供了判断 AI 产出是否正确的客观证据。AI 给出的解释不能替代唯一索引、事务回滚、执行计划或人工页面操作结果。

### 10.2 阶段化协作流程

首次尝试中，AI 根据初始要求一次性生成了完整项目。项目负责人指出这种方式没有留下真实的检查和修改过程，也无法在关键取舍上参与。该成果被保留在 `draft/stage1-ai-initial` 分支，主分支从空白基线重新开始。之后每个里程碑采用下列流程。

**图 10-1 人与 AI 的阶段协作流程**

```text
人工提出当前目标
       ↓
AI 阅读现有代码和文档，提出候选方案
       ↓
人工或独立审阅逐项质疑并作出选择
       ↓
AI 同步设计文档和 TODO，等待确认
       ↓
AI 实现代码、测试与配置并运行自动检查
       ↓
人工在浏览器验收 ──发现问题──→ AI 复现、修复、回归
       │
       └────────通过────────→ 下一里程碑
```

设计文档通常先形成单独提交，例如认证、草稿、题目、跳转、生命周期、填写、提交和统计分别对应 `45b470e`、`5e41b47`、`e0e374d`、`b8b4fff`、`7cddf18`、`05ce3b1`、`3b7357b` 和 `027d2ab`。实现随后使用独立提交保存。这样可以从 Git 历史区分“已确认的规则”和“按照规则写出的代码”，也方便检查实现是否偏离设计。

### 10.4 代表性的 AI 输出修正

第一类修正发生在推进方式。AI 最初追求一次性交付，但项目负责人需要的是可观察的人机协作过程。人工否决后，仓库改为每个里程碑先讨论再实现，未通过检查的内容不会继续扩展。

第二类修正发生在跳转图。早期候选为每道题保留默认下一题边，这会让从第一题沿默认边到达所有题，`QUESTION_UNREACHABLE` 永远无法出现。审阅指出逻辑矛盾后，系统只在规则可能不命中时保留默认边，并为必答单选全覆盖去掉默认边。共享逻辑测试随后覆盖 Q1 的全部选项跳到 Q3、Q2 不可达的例子。

第三类修正发生在统计游标。初始方案使用签名 Base64URL 保存 `submittedAt` 与 ObjectId。签名只能防篡改，创建者仍可解码载荷，因而泄露匿名提交的精确时间。审阅后改为 AES-256-GCM，加入随机 IV、认证标签和资源绑定；测试确认游标不能解析为 JSON，也找不到时间或 ID 明文。

第四类修正发生在登录有效期。候选方案曾考虑创建填写会话时重签两小时登录 Cookie，项目负责人指出这会形成滑动续期，与“泄露令牌最多使用到固定到期”矛盾。最终取消刷新，登录过期后要求同账号重新认证，并继续使用仍有效的填写 Cookie。

这些例子说明，AI 适合快速列出方案和实现细节，但容易忽略跨阶段约束。项目把人工质疑、自动测试、数据库不变量和 Git 检查点组合起来，避免依赖一次回答的表面完整性。

### 10.5 过程记录与敏感信息处理

`docs/AI_USAGE_LOG.md` 从需求阶段开始记录提示目标、AI 产出、人工意见、修改和复测。日志保留当时真实的测试数字，例如 173、177、181 和 184，不用最终结果覆盖历史过程。实验文件保存命令、数据规模和脱敏输出；代码提交保存阶段边界。

### 11.1 从零启动与环境统一

项目负责人安装并启动 Docker Desktop，通过 nvm 使用实际验证的 Node.js 24.22.0；项目文件则把 `.nvmrc`、`engines.node`、README 和锁文件统一到同一版本。依赖表逐项读取 `package-lock.json`，MongoDB 版本读取 `docker-compose.yml`。Homebrew MongoDB 曾占用 27017，另一个副本目录还留下固定名称容器；项目停止 Homebrew 服务、移除 Compose 的 `container_name`，以后以当前目录的 Compose 项目隔离容器。最终从原目录完成 `npm ci`、类型检查、测试、构建、格式检查以及数据库停启恢复，里程碑 1 才标记为通过。

### 11.2 数据库停止后健康检查仍显示已连接

**发现。** 项目负责人停止 MongoDB 容器后，页面仍显示 `connected`，后端也没有断开日志。

**根因。** `getDatabaseStatus()` 只读取 Mongoose 的被动 `readyState`。驱动没有立即发出状态变化时，该值不能证明数据库此刻能够响应。自定义五秒重连也只覆盖首次连接失败，README 却把它描述为所有断线场景。

**修改与复测。** 健康检查在 readyState 为连接后继续执行 `db.admin().ping()`，并增加两秒应用超时；路由改为异步返回 `ok` 或 `degraded`。第一次复测因 Homebrew MongoDB 占用 27017 而连错实例，结果作废。随后把临时测试 MongoDB 隔离到 27018，停库前返回 `ok/connected`，停库后连续五次均为 `degraded/disconnected`，恢复后重新连接。三项数据库状态回归测试同时通过。

### 11.3 默认边使不可达检查失效

**发现。** 跳转设计审阅发现，如果每题始终有“进入下一题”的默认边，从第一题沿默认边便能到达所有题，任何数据都不会触发 `QUESTION_UNREACHABLE`。

**根因。** 候选图模型把运行时的兜底路径当成无条件边，没有考虑必答单选且规则覆盖全部选项时，填写者不可能走默认路径。

**修改与复测。** 精确图仅在规则可能全部不命中时保留默认边；必答单选的 equals 规则覆盖所有选项时移除默认边。循环报告也改为定位目标不晚于来源且确实位于回路中的规则边，避免依赖 DFS 遍历顺序。共享包测试覆盖不可达、直接与间接循环、重排后回跳、最短回路和固定种子对拍，人工发布检查也确认错误与警告定位正确。

### 11.4 匿名分页游标泄露精确时间

**发现。** 统计设计审阅把候选游标做 Base64URL 解码，发现载荷直接包含精确 `submittedAt` 和带时间信息的 ObjectId，与匿名页面只显示 UTC 日期的承诺冲突。

**根因。** HMAC 签名保证完整性，不提供机密性。即使创建者不能修改游标，也仍能读取明文载荷。

**修改与复测。** 文本回答和实名提交记录游标改用 AES-256-GCM，密钥从 JWT 密钥和专用域标签派生，并用 AAD 绑定接口 kind、问卷、版本和题目。测试验证正常分页、篡改拒绝、跨接口复用拒绝，并扫描游标明文，确认不能解析出合法 JSON、时间或 ObjectId。

### 11.6 自动测试发现的实现偏差

草稿集成测试曾发现空说明被 Mongoose `required` 拒绝，测试限流状态又在用例间残留。模型改为允许空字符串，测试前重置限流器。随后测试发现 Mongoose 自动时间戳使版本和问卷的 `updatedAt` 相差数毫秒；事务改用同一个显式 now，并对两次更新关闭自动时间戳。

统计游标测试还发现，简单修改 Base64URL 最后一个字符可能只改变编码中的未使用位，解码后的字节没有变化，导致“篡改”用例偶发仍合法。测试改为修改确定参与密文或认证标签的字节，再验证 GCM 认证失败。以上问题都由自动测试先失败后修正，没有把不稳定测试当作业务成功证据。

### 11.7 经验总结

## 第 12 章 总结与第二阶段基础

### 本章要点

- 第一阶段已经形成从设计、实现、测试到人工验收的完整闭环。
- 版本快照和按版本回答隔离解决了发布后修改导致历史语义漂移的问题。
- 当前边界被明确记录，不以课程环境的测试通过代替生产就绪声明。
- 第二阶段可以在稳定 ID、不可变版本和 `schemaVersion` 基础上做需求差异扩展。

### 12.1 第一阶段成果

本项目完成了初始需求要求的系统设计、数据库设计、前后端程序、必要测试、项目文档和完整报告。功能上，账号、问卷草稿、四种题型、答案校验、条件跳转、发布检查、版本历史、匿名或实名填写、重复限制、幂等提交和按版本统计已经连成可操作流程。数据库层面，五个集合的职责、内嵌与拆分理由、索引、事务、TTL 和聚合均有代码、测试或执行计划证据。

系统最重要的结果不是页面数量，而是建立了稳定的数据语义：每个发布版本是不可变快照，每份填写会话和回答明确绑定版本，服务端重新计算实际路径，旧回答不会因新版本修改而改变含义。事务、revision 条件更新和唯一索引分别处理跨文档原子性、乐观并发和最终唯一性，三者没有互相替代。

测试采用共享逻辑单元测试、真实 MongoDB API 集成测试、Vue 测试、大规模 `explain()` 实验和人工端到端验收。最新 184 项自动测试全部通过，人工流程发现的退出消息残留、填写页账号切换和实名提交记录缺口也已转化为回归测试。AI 使用过程保留候选、质疑、修改和复测，而不是只展示最终生成结果。

### 12.2 已知边界

当前实现适合课程本地环境，但仍有以下明确边界：

- 进程内存限流在 API 重启后清空，多实例之间不共享；
- JWT 固定两小时到期，不提供刷新、黑名单或服务端即时撤销；
- `ANONYMOUS_ID_SECRET` 不能直接轮换，否则既有 ownerKey 的会话所有权和去重失效；
- 匿名仅保证创建者接口看不到直接身份，运维密钥、小样本内容和提交相对顺序仍可能带来重新识别风险；
- `sessionStorage` 草稿只存在当前浏览器会话，清理浏览器数据后无法恢复；
- 单节点副本集提供事务但不提供高可用，统计基准也只代表本次硬件和数据分布；
- 第一阶段不提供整份问卷删除、归档、跨版本自动合并统计或协同编辑。

这些边界已经进入设计、API 和测试追踪文档。报告不把未实现能力包装为完成项，也不把未来建议写成现有保证。

### 12.3 第二阶段的可扩展基础

第一阶段为后续需求变化保留了四类基础。第一，稳定的 surveyId、publicId、questionId、optionId 和 ruleId 允许比较版本并保持外部链接不变。第二，发布版本不可变、回答保存 `surveyVersionId` 和实际 `questionPath`，使第二阶段可以准确说明修改前后差异。第三，`schemaVersion` 为版本文档迁移预留入口，服务、模型和共享纯函数的边界也便于增加规则而不把数据库操作带入前端。第四，回答独立集合和以版本为首键的索引，为数据增长、归档或分片讨论提供明确访问模式。

如果第二阶段要求面向生产或增加新功能，应先做需求差异分析，再决定迁移而不是直接修改历史版本。可能的工程演进包括：把限流迁移到 Redis；加入可撤销会话与密钥版本；把本地副本集升级为受监控的多节点部署；为归档和删除定义保留策略；为高敏感问卷增加最小样本显示或差分隐私；在题型与规则扩展时提升 `schemaVersion` 并提供向后兼容读取。它们是基于当前边界的演进方向，不属于第一阶段已经实现的功能。

### 12.4 结论

第一阶段证明了版本化问卷可以利用 MongoDB 文档模型保存自包含版本，同时把持续增长的回答拆为独立集合。通过人工决策、AI 辅助、数据库约束和多层测试的组合，系统在功能之外还获得了可解释的设计理由和可复现证据。当前 Markdown 报告、设计文档、API、实验记录和代码共同构成第二阶段的基线；后续修改应继续遵守“先明确差异、再修改、保留旧版本、用证据验收”的流程。

|  400 | `VALIDATION_ERROR`、`ANSWER_VALIDATION_FAILED`                                                                               | 请求结构、字段或真实路径答案错误         |
|  401 | `AUTH_REQUIRED`、`AUTH_INVALID`、`INVALID_CREDENTIALS`                                                                       | 缺少登录、令牌失效或凭据错误             |
|  403 | `ORIGIN_NOT_ALLOWED`                                                                                                         | 写请求来源不允许                         |
|  404 | `NOT_FOUND`、`SURVEY_NOT_FOUND`、`QUESTION_NOT_FOUND`、`PUBLIC_SURVEY_NOT_FOUND`、`SESSION_NOT_FOUND`                        | 路由或资源不存在，也用于隐藏越权资源     |
|  409 | `USERNAME_TAKEN`、`VERSION_NOT_EDITABLE`、`DRAFT_CONFLICT`、`SURVEY_LIMIT_REACHED`、`QUESTION_LIMIT_REACHED`                 | 唯一性、草稿状态、并发或数量冲突         |
|  409 | `QUESTION_REFERENCED`、`OPTION_REFERENCED`、`PUBLISH_BLOCKED`、`PUBLISH_WARNINGS_UNCONFIRMED`                                | 引用保护或发布闸门                       |
|  409 | `DRAFT_ALREADY_EXISTS`、`SURVEY_NOT_PUBLISHED`、`SOURCE_VERSION_NOT_CURRENT`、`VERSION_NOT_PUBLISHED`                        | 版本生命周期冲突                         |
|  409 | `SURVEY_CLOSED`、`SURVEY_EXPIRED`、`SESSION_EXPIRED`、`SESSION_LIMIT_REACHED`、`ALREADY_SUBMITTED`、`SURVEY_VERSION_INVALID` | 填写状态、重复提交或版本结构异常         |
|  413 | `PAYLOAD_TOO_LARGE`                                                                                                          | 请求正文超过对应上限                     |
|  415 | `UNSUPPORTED_MEDIA_TYPE`                                                                                                     | 带正文请求未使用 JSON                    |
|  429 | `RATE_LIMITED`                                                                                                               | 请求超过窗口上限，响应包含 `Retry-After` |
|  500 | `INTERNAL_ERROR`                                                                                                             | 未预期服务错误                           |
|  503 | `STATISTICS_UNAVAILABLE`                                                                                                     | 统计超时或无法取得一致快照               |

发布检查结果代码不是 HTTP `error.code`。`EMPTY_SURVEY`、`INVALID_STRUCTURE`、`DEADLINE_PASSED` 和 `JUMP_CYCLE` 是阻止项；`QUESTION_UNREACHABLE` 与 `SHADOWED_RULE` 是警告。检查接口即使发现阻止项也返回 200，并通过 `valid: false` 表示不可发布；真正发布时才映射为 `PUBLISH_BLOCKED`。

### 13.4 术语表

**表 13-3 关键术语**

| 术语                 | 含义                                                                            |
| -------------------- | ------------------------------------------------------------------------------- |
| `publicId`           | 问卷稳定公开链接标识，发布新版本时不改变                                        |
| `internalName`       | 仅创建者可见的问卷管理名称，不等于填写者看到的标题                              |
| `currentVersionId`   | 当前对新填写者公开的已发布版本指针                                              |
| `draftVersionId`     | 当前唯一下一版本草稿指针                                                        |
| `versionNumber`      | 同一问卷内从 1 开始递增的业务版本号                                             |
| `revision`           | 草稿每次成功写入后增加的乐观并发号，不等同于 versionNumber                      |
| `ownerKey`           | 由问卷 ID、账号 ID 和服务端密钥生成的问卷内 HMAC 假名，用于会话所有权和重复识别 |
| `dedupKey`           | 禁止重复时写入回答唯一索引的键，当前由 ownerKey 派生                            |
| `activeSlot`         | 同账号同问卷最多五个活动会话中的槽位，提交或过期后释放                          |
| `survey_session`     | 两小时登录 JWT 的 HttpOnly Cookie                                               |
| `survey_fill`        | 特定填写会话的 HttpOnly Cookie，Path 限定到该会话 API                           |
| `questionPath`       | 服务端按正式答案重新计算并随回答保存的实际到达题目顺序                          |
| `ignoredQuestionIds` | 提交中存在但不在真实路径上、因此未保存答案的已知题目 ID                         |
| `identityMode`       | 版本级身份展示模式：`anonymous` 或 `identified`                                 |
| `manualStatus`       | 问卷级人工开关：`open` 或 `closed`，与由版本截止时间计算的 `expired` 分离       |
| `schemaVersion`      | 问卷版本文档的结构版本，为后续兼容读取与迁移预留                                |

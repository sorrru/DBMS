# 里程碑 10：系统测试补缺与实验记录计划

## 文档状态

本方案由项目负责人与 AI 于 2026-10-20 讨论并确认。里程碑 10 不扩展业务范围，也不重新实现已有测试；先建立需求—测试追踪矩阵，只对证据为空的行为补测试，再执行种子、查询计划、完整回归和人工端到端验收。

当前自动测试基线为共享逻辑包 11 项、API 140 项、Web 22 项，共 173 项。现有执行计划证据包括版本历史倒序扫描和 50,000 份回答的统计聚合与文本分页。

## J1–J12 已确认方案

1. 新增 `TEST_TRACEABILITY.md`，按可独立验收的业务行为关联需求、自动测试、人工证据和状态，不机械复制每一个断言。
2. 固定当前 173 项测试、Node/npm/MongoDB 版本、构建与格式结果为补缺前基线；最终数量必须重新实测。
3. 第一轮只补五个明确缺口：不同问卷 ownerKey、过期活动槽释放、发布版本不可变矩阵、统计跨版本隔离、问卷列表 explain。
4. 已有并发和事务测试只做证据汇总，不重复编写等价测试。
5. 扩充种子数据，使匿名统计包含三份可手算回答，实名统计至少包含两份回答，并继续覆盖多版本、跳转、关闭、到期和旧会话。
6. 在受保护本地库实际执行两次 seed、两次 clean，并记录集合计数，确认重复运行和清理幂等。
7. 保留已有两份 explain，新增问卷列表复合索引与游标范围的实际执行计划，并建立索引证据总览。
8. 新增 `docs/experiments/MILESTONE10_TEST_REPORT.md`，按测试文件或业务场景记录环境、命令、预期、实际、结果和修复，不把报告写成 173 条断言的日志副本。
9. 最终依次运行 `npm ci`、类型检查、完整测试、生产构建和格式检查，记录准确数量与耗时。
10. 人工端到端验收分成认证、编辑发布、填写提交、历史统计四组，由项目负责人操作；AI 不代替人工启动网站或点击。
11. 验收发现问题时遵循“记录复现 → 失败测试 → 修复 → 定向复测 → 完整回归 → 单独提交”。
12. 追踪矩阵无未解释空白、五个缺口关闭、种子和 explain 有实测证据、自动与人工验收均通过后，里程碑才完成。

## 五个待补缺口

| 编号 | 缺口                                                   | 计划证据                                                                                                          | 预计改动                           |
| ---- | ------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------- | ---------------------------------- |
| P1   | 同一账号在不同问卷下必须得到不同 ownerKey              | 创建两份问卷与匿名会话，直接比较数据库 ownerKey；同时确认同一问卷跨版本保持稳定                                   | `fill-session.integration.test.ts` |
| P2   | 已过期但 TTL 尚未清理的活动会话必须释放五个 activeSlot | 预置五个过期 active 会话，再创建新会话；断言成功、旧会话转为 expired 且 activeSlot 清空                           | `fill-session.integration.test.ts` |
| P3   | 已发布版本所有写接口均不可修改                         | 对设置、题目增删改排序、规则 PUT、validate 和再次 publish 建立参数化不可变矩阵，统一断言 `VERSION_NOT_EDITABLE`   | 问卷与题目集成测试                 |
| P4   | v1、v2 的统计结果不能混合                              | 两个发布版本分别写入不同数量和不同答案，逐版本查询并断言总数、选项与文本均隔离                                    | `statistics.integration.test.ts`   |
| P5   | 问卷列表分页实际使用 `{ ownerId, updatedAt, _id }`     | 用足量固定数据在事务外运行 `explain("executionStats")`，记录 winningPlan、索引、keys/docs examined 与是否阻塞排序 | 新实验脚本与文档                   |

P1–P4 是测试证据缺口，未预判生产代码一定存在缺陷；测试变红后才进入修复流程。P5 是执行计划证据缺口，不更改查询语义。

## 第一轮补缺结果

P1–P4 新增的四项集成测试全部首次通过，说明它们是证据缺口，没有暴露生产逻辑缺陷。P5 使用 10,000 份固定本地数据实测：首屏和中点游标页均由优化器自行选择 `ownerId_1_updatedAt_-1__id_-1`，返回 21 条时各检查 21 个索引键和 21 份文档；游标页以两个有序索引区间的 `SORT_MERGE` 合并，不存在阻塞排序。完整证据见 `docs/experiments/MILESTONE10_SURVEY_LIST_EXPLAIN.md`。

补缺后自动测试数量为共享逻辑 11 项、API 144 项、Web 22 项，共 177 项；此处仅记录定向测试通过，最终完整回归仍按 J9 单独执行和记录。

## 种子数据验收目标

扩充后的固定小数据至少满足：

- 匿名已发布 v1 有三份回答，包含两条不同实际路径、未到达题、零计数选项和数字答案；
- 匿名问卷仍有 v2 草稿，证明统计固定绑定 v1；
- 实名已发布问卷有两份回答，文本页能显示两个账号且服务端只批量查询一次用户；
- 保留关闭问卷、到期问卷、过期旧会话、允许与禁止重复提交样例；
- 文档列出每题人工可算的预期提交数、到达数、回答数和选项/数字结果。

种子验证只清理脚本自有账号和关联数据，不删除项目负责人手工创建的账号或问卷。脚本继续拒绝生产环境、`mongodb+srv` 和非本地主机。

## 最终输出

- `docs/TEST_TRACEABILITY.md`：需求—测试追踪矩阵；
- `docs/experiments/MILESTONE10_TEST_REPORT.md`：自动测试和人工验收记录；
- 问卷列表分页 explain 及索引证据总览；
- P1–P4 新增测试以及测试暴露问题时的对应修复；
- 可重复生成、清理且可人工核算的种子数据。

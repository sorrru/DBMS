# 里程碑 5：跳转规则与发布检查设计

本文固定草稿跳转规则、共享路径计算和发布前检查的候选方案。里程碑 5 只完成规则编辑、运行语义和发布闸门；真正发布版本、切换指针和历史版本管理留到里程碑 6。

## 已确认的原则

- 每道题的规则整组保存，数组顺序就是优先级；多条规则命中时第一条生效。
- 草稿允许暂时包含循环或不可达题目，保存规则和发布检查分开处理。
- 循环、空问卷和已经过去的截止时间阻止发布；不可达题目和重复条件只产生警告。
- 后端在里程碑 6 的发布事务内重新调用同一检查函数，不信任先前检查结果。

## 共享逻辑包

新增无框架、无数据库依赖的 npm workspace `packages/survey-logic`，由前后端共同引用。它从建立之初就是以下规范类型和纯函数的唯一实现位置，API 与前端不得保留副本：

- `validateAnswer(question, value)`：保持里程碑 4 已确认的返回结构和规范化语义。
- `evaluateNextQuestion(questions, currentQuestionId, answer)`：计算当前题之后的一个节点。
- `computePath(questions, answers)`：从第一题计算实际路径，维护已访问集合，遇到异常循环返回结构化错误，绝不死循环。
- `validateForPublish(version, now)`：生成发布阻止项和警告；`now` 显式传入，测试不依赖系统时间。

共享包不得导入 Vue、Express、Mongoose 或 Node 专属 API。`apps/api` 继续负责请求、权限、事务与持久化，`apps/web` 负责交互。

共享包使用与现有项目一致的 ESM 和带 `.js` 扩展名的内部导入。其 `package.json` 固定 `main`、`types` 和 `exports` 指向编译后的 `dist`，生产构建不直接引用另一个 workspace 的 `.ts` 源码。根工作区显式按“共享包 → API → Web”顺序构建，不依赖 npm glob 的偶然顺序。

开发命令先完成一次共享包构建，再同时运行共享包 TypeScript watch、API watch 和 Vite；API 与 Vite 从包的 `exports` 解析 `dist`，并在共享包输出变化时重新加载。实现后必须在全新安装状态重新验证 README 的检查和开发启动步骤。

## 规则结构和上限

规则使用扁平结构，废弃系统设计中旧的嵌套 `condition` 写法：

```json
{
  "ruleId": "r_URL安全随机值",
  "operator": "containsAny",
  "value": ["o_lecture", "o_lab"],
  "targetQuestionId": "q_follow_up"
}
```

- `ruleId` 由服务端生成，格式为 `^r_[A-Za-z0-9_-]+$`，规则移动不改变 ID。
- 新规则不带 `ruleId`；保留旧规则时必须提交属于该来源题的原 ID。
- 重复、伪造或借用其他题目的规则 ID 均拒绝。
- 每题规则上限默认 20 条，由 `JUMP_RULE_MAX_PER_QUESTION=20` 配置；启动时要求它是 1–100 的整数，否则拒绝启动。超限返回 `400 VALIDATION_ERROR`。
- `jumpRules` 子文档关闭 Mongoose 自动 `_id`。

## 操作符和匹配

| 来源题型 | 操作符                             | `value` 规范形态            |
| -------- | ---------------------------------- | --------------------------- |
| 单选     | `equals`                           | 一个属于来源题的 `optionId` |
| 多选     | `contains`                         | 一个属于来源题的 `optionId` |
| 多选     | `containsAll`                      | 非空、无重复的 `optionId[]` |
| 多选     | `containsAny`                      | 非空、无重复的 `optionId[]` |
| 数字     | `equals`、`gt`、`gte`、`lt`、`lte` | 安全范围内的有限 JSON 数值  |
| 文本     | 不支持                             | 只能保存空规则数组          |

数组型规则值不得超过来源题选项数量。服务端保存前按来源题的选项顺序规范化，不保留客户端的提交顺序。数字 `-0` 存为 `0`，`equals` 使用 JSON 数值的精确相等，不进行浮点容差比较。

规则合法性只取决于来源题型、操作符、值形态和选项归属，不依赖数字题的 `integerOnly`、`minValue` 或 `maxValue`。因此以后修改数值校验不会使已保存规则结构失效；明显永远不会命中的数字规则本里程碑不额外警告。

未回答包括字段缺失、`null`，以及多选题的空数组。未回答时所有规则都视为不匹配，包括 `lt` 和 `lte`，直接走默认边。

`evaluateNextQuestion` 只匹配已经符合 `validateAnswer` 规范形态的答案，不做类型转换。数字字符串 `"5"`、未知单选 ID、多选中的重复或外来 ID 等非规范值一律按未回答处理并走默认边，不在路由阶段抛异常。后端提交时先用这一规则计算路径，再对路径内原始答案调用 `validateAnswer`，因此非规范答案最终仍会被拒绝。

## 跳转执行

`evaluateNextQuestion` 按规则数组从前到后检查，返回：

```ts
{ kind: "question", questionId: string } | { kind: "end" }
```

第一条匹配规则决定目标题；无规则匹配时进入当前数组中的下一题；最后一题无匹配规则时返回 `{ kind: "end" }`。前端不能提交“下一题”或声称的路径作为可信结果。

`computePath` 从第一题开始重复调用该函数。它用已访问节点集合保护异常数据；再次遇到同一题时返回循环错误，而不是继续执行。里程碑 7 用它即时更新页面路径，里程碑 8 用它在服务端重新计算最终路径，然后逐题执行答案校验。

## 规则编辑接口

`PUT /api/surveys/:surveyId/versions/:versionId/questions/:questionId/jump-rules`

请求完整替换一道来源题的全部规则：

```json
{
  "revision": 8,
  "rules": [
    {
      "operator": "equals",
      "value": "o_yes",
      "targetQuestionId": "q_follow_up"
    }
  ]
}
```

已有规则在请求中携带原 `ruleId`，新规则省略 ID。成功返回完整 `{ version, surveyUpdatedAt }`，并使版本 revision 加一。规则写入与 `surveys.updatedAt` 更新使用同一事务和同一时间。

接口沿用题目写入的稳定判定顺序：请求结构与路径格式 → 问卷/版本不存在 → 非草稿 → revision 冲突 → 来源题不存在 → 业务规则。来源题不存在返回 `QUESTION_NOT_FOUND`；目标题不存在、目标题格式错误、条件选项不属于来源题均返回 `400 VALIDATION_ERROR`，`details.path` 指向 `rules[i].targetQuestionId` 或 `rules[i].value`，避免与来源题不存在混淆。

自跳转只能由错误请求产生，保存时返回 `400 VALIDATION_ERROR`，`details.path` 指向 `rules[i].targetQuestionId`。指向更靠前题目的规则允许暂存在草稿中，以便重排后仍保留原规则；发布检查负责判断它是否形成真实循环。前端创建新规则时只列出来源题之后的题目，从源头减少循环；重排使既有规则变为潜在回跳时，使用共享检查函数即时提示。

## 引用保护

加入规则后，题目完整替换必须保留原 `jumpRules`，不能因为保存标题或校验设置而清空规则。

- 题目 PATCH 删除一个被本题规则条件引用的选项时返回 `409 OPTION_REFERENCED`。
- 题目 DELETE 删除一个被其他题规则作为目标引用的题目时返回 `409 QUESTION_REFERENCED`。
- 删除来源题会一并删除它自身的规则；如果它同时被其他题引用，仍然阻止。
- 不静默级联删除或改写规则。

两类错误属于既有错误顺序的第 6 步业务规则，`details.references` 固定为 `{ questionId, ruleId }[]`。

## 发布检查图模型

每道题是一个节点，每条跳转规则提供一条条件边。默认边并非无条件存在：

- 必答单选题的规则覆盖全部现有选项时，任一合法答案必定命中规则，因此不画默认边。
- 非必答单选题仍可能未回答，所以保留默认边。
- 多选与数字题为了避免复杂条件完备性证明，保守地保留默认边。
- 其他未覆盖全部选项的单选题也保留默认边。
- 最后一题的默认结果是结束，不产生题目边。

“覆盖全部选项”只要求每个现有选项至少有一条合法 `equals` 规则，不因重复条件改变。这个有意保守的边界可能少报某些多选或数字题的不可达情况，但不会把可能到达的题误判为不可达。

发布检查先防御性复核结构完整性：目标题存在，条件选项归属正确，题目、选项和规则 ID 在版本内全局唯一，题数与选项数没有超过硬上限。任一失败产生阻止项 `INVALID_STRUCTURE`；这不替代写入校验，而是保护不可逆发布步骤不受旧数据、手工数据或未来迁移错误影响。

从第一题遍历精确构建的图：

- 没有题目时产生阻止项 `EMPTY_SURVEY`。
- DFS 或 BFS 计算从第一题可达的题目集合。
- 对每条规则边 `u → v` 独立判断：`v` 位于 `u` 之前、`u` 从第一题可达，且在精确图中 `v` 能到达 `u` 时，产生一个 `JUMP_CYCLE`。自跳转已经在保存时拒绝。
- `questionIds` 固定返回经过该规则边的最短回路：先列 `u → v`，再用 BFS 取得 `v` 回到 `u` 的最短路径。报告不依赖 DFS 邻接边遍历顺序，也不会错误地把没有规则位置的默认边当成问题来源。
- 未从第一题访问到的节点产生警告 `QUESTION_UNREACHABLE`。
- 同一来源题中操作符和值相同的后续规则产生警告 `SHADOWED_RULE`；数组型值按集合比较、忽略排列顺序，目标不同也不改变“后续条件永远先被前一条截获”的事实。`path` 和 `ruleId` 指向被遮蔽的规则，消息带上前一条规则的位置。

默认边只会向后续题目移动，因此任何真实环都至少包含一条满足上述条件的规则边，不会漏报。循环错误按来源题数组顺序、规则数组顺序排序；不可达和遮蔽警告也按题目顺序、规则顺序排序。与题目无关的结构、空问卷和截止时间结果使用固定代码优先级排在题目结果之前，使相同版本始终得到完全相同的结果顺序。

在全保留默认边的简化模型中，从可达题目指向更靠前题目的规则等价于形成循环。实现仍使用精确可达性判断，因为必答单选全覆盖会移除默认边，使简单位置判断与精确图可能不同。

不可达示例：Q1 是必答单选题，A、B 两个选项都跳到 Q3。Q1 的全部选项已覆盖，因此不画 Q1→Q2 默认边，Q2 被报告为不可达。

## 发布检查接口

`POST /api/surveys/:surveyId/versions/:versionId/validate`

请求固定为 `{ "revision": 9 }`。接口只允许草稿；发布版本返回 `409 VERSION_NOT_EDITABLE`，过期 revision 返回 `409 DRAFT_CONFLICT`。检查不修改任何文档、时间或 revision。

正常完成检查始终返回 HTTP 200，即使不能发布：

```json
{
  "revision": 9,
  "valid": false,
  "errors": [
    {
      "code": "JUMP_CYCLE",
      "path": "questions[2].jumpRules[0]",
      "message": "该规则指向更靠前的题目并形成循环",
      "questionId": "q_3",
      "ruleId": "r_back",
      "questionIds": ["q_3", "q_1", "q_3"]
    }
  ],
  "warnings": [
    {
      "code": "QUESTION_UNREACHABLE",
      "path": "questions[1]",
      "message": "该题无法从第一题到达",
      "questionId": "q_2"
    }
  ]
}
```

`valid` 只由 `errors.length === 0` 决定。截止时间非空且不晚于检查时刻时加入 `DEADLINE_PASSED` 阻止项。里程碑 6 的发布事务必须使用事务内重新读取的草稿和同一 `validateForPublish` 再检查一次。

响应中的 `revision` 是本次实际检查的版本值。每个题目相关结果除 `path` 外都包含稳定 `questionId`，规则相关结果还包含 `ruleId`；`DEADLINE_PASSED.path` 固定为 `deadline`。前端任一写入成功后必须清除或置灰旧检查结果，避免数组下标变化后继续定位旧结果。

检查结果代码与 API 请求错误码分开维护：前者存在于成功响应的 `errors`/`warnings` 项中，后者存在于非 2xx 响应的 `error.code` 中。

### 阻止发布的检查结果

| 代码                | 含义                                       |
| ------------------- | ------------------------------------------ |
| `INVALID_STRUCTURE` | 防御性复核发现版本内部结构不完整或 ID 冲突 |
| `EMPTY_SURVEY`      | 问卷没有题目                               |
| `JUMP_CYCLE`        | 精确图中存在循环；按构成回路的规则分别报告 |
| `DEADLINE_PASSED`   | 版本截止时间已经过去                       |

### 发布警告

| 代码                   | 含义                                     |
| ---------------------- | ---------------------------------------- |
| `QUESTION_UNREACHABLE` | 题目无法从第一题到达                     |
| `SHADOWED_RULE`        | 前面的相同条件会先命中，当前规则不会执行 |

## 前端交互

- 规则区只使用已经保存的题目与选项。当前卡片有未保存的选项改动时禁用规则编辑并提示先保存题目。
- 单选和多选值使用现有选项选择控件，数字规则使用数字输入；目标显示“题号 + 标题”，不显示裸 ID。
- 添加、删除、上移和下移先在本地编辑，点击“保存本题规则”一次提交完整数组。
- 设置、题目和规则继续共享一个版本 revision 与写入锁。
- 目标选择框只列出当前题之后的题目；重排导致的潜在回跳在本地即时提示，后端仍接受并由发布检查准确判断。
- 发布检查结果分为“必须修复”和“可以继续发布的警告”，点击结果定位到对应题目或规则。

## 测试计划

- 覆盖题型与操作符完整矩阵，以及数字 `gt`、`gte`、`lt`、`lte`、精确 `equals`、安全边界和 `-0`。
- 验证第一条命中优先、未回答走默认边、最后一题自然结束和 `computePath` 的已访问保护。
- 拒绝伪造、重复或借用其他题的 `ruleId`；文本题只能保存空数组；第 21 条规则失败。
- 验证目标题不存在、自跳转、条件选项不属于来源题及稳定的 `details.path`；自跳转在保存时失败，循环用指向更靠前题目的规则构造。
- 覆盖直接回跳循环、间接循环、重排后回跳、必答单选全覆盖导致的不可达、空问卷、无效内部结构及重复规则；循环结果包含稳定 ID、最短回路和固定顺序。
- 验证检查接口不修改文档、时间或 revision；非草稿失败，过期 revision 返回 `DRAFT_CONFLICT`。
- 验证被引用题目和选项无法删除，题目 PATCH 保留规则并返回完整引用列表。
- 两个相同 revision 的并发规则 PUT 恰好一个成功。
- 对固定种子的随机小型问卷进行性质对拍：限制为 2–7 题、每个选择题 2–3 个选项；数字题从规则阈值和相邻代表值构造有限候选，多选使用所有子集。沿实际路径惰性枚举，只为已经访问的题目展开答案；非必答题加入未回答候选，必答题不加入。
- 对拍断言：任何实际访问题都属于图可达集合；图判定无环时任何 `computePath` 都不会循环；图判定有环时统计实际存在循环的答案比例，作为保守模型边界的实验证据。
- 种子数据加入一个有效分支问卷，并由受保护测试辅助数据构造不可达、重复规则和循环失败样例。

本设计经人工再次确认后才进入实现。

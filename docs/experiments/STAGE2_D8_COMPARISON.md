# 第二阶段 D8 反向引用方案比较

2026 年 10 月 22 日在 MongoDB 8.0.34、rs0 上比较快照多键索引 A 与独立使用集合 B。三类查询结果均核对一致，选择 B 作为第二阶段反向引用与统计来源索引；问卷快照继续是内容事实来源，使用集合只是事务维护的投影。

## 数据和复现

独立 `survey_stage2_d8_test` 库中构造 2,000 份问卷、6,000 个版本、30,000 条题目实例使用记录，20 个所有者、40 个题目身份。每份问卷含两个发布版本和一个草稿，每个版本五个实例，其中第 5 个实例复用第 1 个实例的题目身份与题目版本，但实例 ID 不同。通过固定 s、v、q 模运算产生数据，不使用随机当前业务数据。

复现命令：`npm run library:usage-benchmark --workspace @survey/api`。脚本拒绝生产环境，只使用硬编码且通过本地主机及 `_test` 校验的专用 URI，不读取应用数据库 URI。只生成、清理 `d8_surveys`、`d8_versions`、`d8_usages` 三个专用集合；不操作开发数据或其他集合。该专用库不要承载其他用途数据。

脚本保存各查询完整 `explain("executionStats")` 到 `STAGE2_D8_RESULTS.json`。JSON 中的 ObjectId 和命名空间均为实验数据。版本字段对齐后对两方案结果做深比较，不仅比较行数。ownDetails 返回 20 个实例，othersSummary 返回 9 个用户与版本及状态分组，statisticsSources 返回 200 个实例。

## 实测计划

A 首先命中 `questions.source.libraryQuestionId_1` 多键索引，展开匹配实例，再通过 `$lookup` 关联问卷 `_id_` 索引取得所有者。B 命中 `libraryQuestionId_1_ownerId_1_status_1_surveyVersionId_1_questionId_1`，在使用记录过滤所有者和状态。

| 查询               | 方案 | 主游标 keysExamined | 主游标 docsExamined | lookup keysExamined | lookup docsExamined | executionTimeMillis |
| ------------------ | ---- | ------------------- | ------------------- | ------------------- | ------------------- | ------------------- |
| 自己明细前 20 项   | A    | 600                 | 600                 | 750                 | 750                 | 21                  |
| 自己明细前 20 项   | B    | 300                 | 300                 | 无                  | 无                  | 0                   |
| 他人使用分组       | A    | 600                 | 600                 | 751                 | 751                 | 20                  |
| 他人使用分组       | B    | 452                 | 450                 | 无                  | 无                  | 1                   |
| 自己已发布统计来源 | A    | 600                 | 600                 | 500                 | 500                 | 14                  |
| 自己已发布统计来源 | B    | 200                 | 200                 | 无                  | 无                  | 0                   |

主游标与 lookup 的计数是不同阶段的指标，不互相替代；lookup 次数随同题多实例展开而增多。B 的自己明细仍需候选扫描和排序，当前索引没有让 limit 20 等同于只扫描 20 条。`0 ms` 为 MongoDB 本次毫秒计时结果，不是查询无成本。单次实验、所有者与题目分布相关、数据量有限，不能推导所有工作负载下 B 必然更快。

## 写入代价与一致性选择

本数据每个版本五个来源实例，B 比 A 增加五条使用记录。复制下一问卷草稿时每实例插入一条，发布每实例更新状态，换题或转本地时替换或删除对应记录，放弃草稿删除整版记录。A 只随快照写入来源字段。此处统计的是额外操作数量，没有实测事务写入耗时，不把它写成写性能结论。

B 的 `(surveyVersionId, questionId)` 唯一索引阻止同实例重复登记，另外两个复合索引支持身份级和版本级过滤。ownerId、status 等字段有意冗余，须由同一事务与草稿操作、发布维护，不能由客户端独立写入。里程碑 2 实现这套维护逻辑，里程碑 3 才提供他人使用分级查询。里程碑 1 只建立 schema、索引和内部冻结原语，既有问卷不补造使用记录。

选择 B 的理由是本任务明确需要按所有者过滤、跨用户脱敏分组与按版本解析来源，B 能直接索引这些边界，并减少统计来源解析的关联操作。代价是写放大和修复责任：后续实现必须覆盖添加、换题、删除、转本地、复制草稿、发布及放弃；提供以快照为准的核对与修复检查。使用记录删除不解除题目永久冻结。实际问卷标题、题目定义与来源映射仍须回读快照，不把冗余状态当成最终授权依据。

回答聚合另按已确认规则执行：先解析当前用户合法的版本与实例映射，再对 `responses` 作版本首要过滤；回答管道不 `$lookup` 回查题库。D8 实验未生成回答，也不声称验证了未来跨问卷回答聚合性能。
